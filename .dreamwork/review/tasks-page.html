The browser guard builds its own git target, and the shared fixture is left alone

dev/capture/fixture is not a repository and holds no tasks.md, so every check run against the shared server would pass against nothing — the trap burndown.mjs, provenance.mjs, gitrow.mjs and dashboard.mjs each name in their own headers. History is planted, so the numbers are known rather than read off the page and compared to itself. The fixture is deliberately not seeded: seeding it can make a neighbouring guard vacuous without making it red, which is the worse of the two failures.

It is written on dev/capture/report.mjs, the shared reporter #192 landed after this proposal was drafted. A guard that imports it inherits four obligations by construction rather than by memory: the exit-handler crash sentinel (so a partway crash prints its checks plus a FAIL, where a tail-printer printed nothing and a FAIL-grep read the silence as a clean sheet), present() absence-first so absence costs one named line instead of a 30-second timeout that points at the guard rather than the page, no count offered at all (a grep -c once reported 6 FAILs where the output held 14), and a declare({drives, traceWindow}) that throws on a missing half. That last one is not documentation: a guard which watches long enough sees a later tick supply the motion it was asserting.

His rulings — answered 21:47, and binding

All seven were answered. They are recorded here as decisions, not recommendations, because a proposal that still argues its own refuted option is one that gets built wrong. Three overrode the recommendation, and the body of this page has been amended to state his call rather than to argue against it.

Q1
May /tasks claim a wider column on a wide screen — a two-pane list-plus-detail triage layout?
Approved, at its own route — “yes, but at /tasks2, and keep a simpler one-column variant at /tasks”. So the recommendation (no, for v1) is overruled, and the argument against a second width exception is not a reason to skip the layout — it is the reason the wide one gets its own address. /tasks2 is #328 and is outside this plan; what this plan owes it is a seam and no second parser: ledger_index and the record shape, taskRow/taskFacets, and a container-agnostic buildTaskDetail. It inherits /review's post-#305 split idiom — the measured window-tall pane, the keyboard-operable gutter separator, the CSS-clamped ratio, the persisted width — rather than authoring a second one.
Q2
Default sort: priority band first, or newest id first (the file's own order)?
Priority then newest id — accepted, “but user configurable alongside filters”. So sort is a control, not a constant: a third .sgroup in the controls row beside the two filter groups, single-select, drawn above. The URL key was already s, which is what makes this a UI addition rather than a contract change — and the default is never written into the URL, so ?t=281 stays the short canonical form #282 hardcodes.
Q3
Default filter: open only, or everything?
Open only — as proposed, with the landed count in the count line and one click away.
Q4
Is /tasks?t=281 the URL #282 should hardcode?
Yes — as proposed. #282 may hardcode it.
Q5
Should the loop's in-flight signal be shown at all, given it is a claim and not a fact?
Show it, but say “in progress” — the hedge is rejected. No “this is a claim” label; the honesty is carried by a hover box reading Reported: Xm Ys ago.

His version is better, and the reason shapes the rest of the copy: freshness is a fact, where “the loop's claim” is a disclaimer. A disclaimer admits the page might be wrong and leaves the reader no way to tell; a measured age makes staleness legible — four seconds ago and forty minutes ago read differently, and only the measurement says which one he is looking at. Anywhere this page hedged where it could instead show a measurement has been changed the same way. The formatter already exists (agePair renders 05m 23s); the age is the age of the claim, never of the render.
Q6
Do you want a write affordance on a row later — do now: #281 sent straight from the list?
Not approved, and not in scope. He asked what it would mean rather than answering, and it has been re-asked as its own question. Nothing here assumes it: the read-only constraint stands and no increment adds a POST seam.
Q7
File the bugs found on the way?
Yes — as proposed. Both original findings have since been fixed by other tasks (#301/#315 and #302); the section above now carries the four measured findings that replaced them.

/filedata is the standing precedent for a route-scoped fetch. The client caches /tasksdata and invalidates on a changed /mtime, so liveness is unchanged and the cost is paid only where it buys something. #282's hovercards fetch one record — which is why the single-record shape exists at all.

And the client-side scan has a named ceiling rather than a discovered one: at ~600 records or a list body over ~512KB, search moves behind #294's query API. The denominator is records, not entries, and that changed the headroom: 148 entries plus 87 pruned ids is 238 records, and the count is monotonic — grooming turns an entry into a pruned record rather than removing it, so it never falls. Under 3× headroom, where against entries alone it read as 4×. The pytest compares the real serialised body to the ceiling constant and prints the measured size; it must never assert today's value, which is a literal with an invisible expiry date.
