Who is trusted on the public internet?

decision review · task #275 · design & research only — public/WAN stays forbidden until a design is approved

A public Dreamhub holds the operator's typed words, repository contents and an autonomous coding loop's working state — and, if any write route were exposed, remote control of that loop. Today 127.0.0.1 is the authorisation model. Going public removes that boundary, so this artifact defines what has to replace it before a single bind address changes.

NO IMPLEMENTATION. This is prose plus a threat model. It changes no .py file, no bind/listen logic, adds no dependency, and defines no flag that could be switched on. Public/WAN support is forbidden until the human approves a reviewed design.
Current posture — why loopback is the auth model

dreamhub.py binds 127.0.0.1 by construction and is read-only; watch.py is loopback by default with an explicitly unauthenticated trusted-LAN mode (#233) whose Host+Origin checks are rebinding/CSRF safeguards, not client auth. Three load-bearing facts shape any public design:

  • The hub serves data that is fine over localhost and dangerous over a link. /data.json "carries the full text of DREAMWORK.md, questions.md and lessons.md… exactly what stops being fine over a link" (dreamhub-design.md).
  • It can display the human's typed words and repository contents — questions, answers, notes, dreams, the task queue, agent ownership, the /file viewer. This is the privacy ceiling.
  • watch.py has six write routes (/answer, /ask, /comment, /command, /tint, /run-mode) that the loop reads back and acts on. Publicly exposing writes is remote steering of an autonomous agent — the take-over class task #288 already proved is real.
Threat model — who the actual adversary is
assets
The human's typed words (highest sensitivity); private repo contents via /file; task queue, agent state, dream transcripts; and write authority over the loop if any write route is exposed.
drive-by
Internet scanners & credential-stuffers probe any public HTTP service within minutes. "Nobody knows the URL" is not a control.
cross-site
CSRF/XSS driving the operator's logged-in browser. CSRF on a write route is the high-value target; read routes leak via XS-Read if SameSite is wrong.
targeted
Someone who knows the operator/project, wanting read of private data or write/steer of the loop. The latter is the take-over case a design must refuse to enable.
token theft
XSS, log leakage, stolen device. The session is the live authority; its lifetime and revocation matter.
the IdP itself
A compromised or rogue identity provider that can mint assertions for attacker accounts — a trust root until an operator allowlist sits in front of it.
trust roots
TLS CA chain · the IdP's signing key · an operator-managed authorisation allowlist. Authentication ("a valid Google account") is never authorisation ("the operator's Google account").
shoo.dev — what its primary sources actually say

Read from shoo's own docs, not hearsay. Shoo is "a minimal auth broker for Google sign-in" — a hosted PKCE OAuth intermediary, not a tunnel and not an authorisation system.

The "Open source" claim is not yet verifiable; the server implementation is unauditable today. No published security review, threat model, uptime or SLA.
Three hard constraints that shape any design
C1 · stdlib
The hub is pure-stdlib Python, single-file, no build step. Python's stdlib cannot verify an ES256/RSA signature — only cryptography (third-party) can. Verified directly: hashlib/hmac are symmetric-only, ssl exposes no general verify. So shoo's tokens cannot be verified in the hub without breaking stdlib-only, shelling to openssl, or a hand-rolled P-256 footgun.
C2 · data
/data.json leaks full DREAMWORK.md/questions.md/lessons.md today. A redacted /summary.json must ship before any public serve.
C3 · writes
Write routes are steering. A read-only public surface is a defensible increment; read+write public is a different, larger, dangerous thing and should not be assumed.

C1 is the single most load-bearing finding for the recommendation: shoo integrated directly into the hub breaks the architecture, because verifying its ES256 tokens in-process is impossible on stdlib alone.

Options, with real trade-offs
A · shoo integrated directly into the hub

Hub gains /auth/shoo (PKCE + JWKS ES256 verify), sets a session cookie, gates routes on a pairwise_sub allowlist.

✗ breaks C1 (needs cryptography/PyJWT or a hand-rolled footgun) · ✗ maturity (WIP, repo 404, unauditable) · ✗ Google-only · ✗ trust-concentrates on ping.gg as sole boundary

Right identity primitive, wrong sole boundary — today.

B · reverse-proxy auth boundary, hub stays loopback ★ recommended shape

A mature TLS-terminating, authenticating proxy fronts the hub. The hub keeps binding 127.0.0.1, accepts only the proxy's signed header, gains zero auth code.

✓ preserves C1 · ✓ TLS handled by proxy · ✓ identity/authorisation at the edge · ✓ mature & audited · shoo can be the IdP behind it later

B1 Cloudflare Access (Zero Trust, free tier) · B2 Tailscale Funnel+ACL · B3 Caddy/nginx + oauth2-proxy.

C · private overlay — not actually public

Tailscale/WireGuard, no Funnel. The network is the boundary; no app-layer auth or TLS needed.

✓ safest · ✓ zero public surface · but requires a client on every device · ✗ not "public"

If the real need is "me, on my devices, away from my desk", C is strictly safer than B.

D · SSH tunnel / bastion

ssh -L to a bastion; already used for remote projects.

~ familiar, strong transport · ✗ awkward on mobile, impossible in a borrowed browser

Reasonable fallback, not the design.

Explicitly rejected
  • E1 · bearer token as the sole public boundary (the #276 LAN design extended to WAN) — tokens leak into logs/referrers/history; revocation manual; non-starter without TLS. #276's scope, not #275's.
  • E2 · mTLS client certs — strongest transport auth, but provisioning certs on phones is painful enough to break the "check from my phone" use case.
  • E3 · hand-rolled P-256 ECDSA verifier — would technically keep stdlib-only at the cost of a security-critical primitive written by an agent. Named as a trap, not a plan.
  • E4 · "any valid IdP token = authorised" — authentication ≠ authorisation. Every option still needs the operator allowlist.
Recommended shape (B) — architecture

The one invariant a bug breaks: the hub must stay loopback-only even behind the proxy, and the proxy must overwrite (never trust client-supplied) auth headers. Shoo appears here as an optional future IdP behind the proxy — not as the boundary itself.

Per-axis definition — recommended shape (B)
AxisDesign
identityDecided at the proxy (Google / GitHub / email OTP / tailnet). The hub never sees a password. Operator maintains a fixed allowlist of one or two identities who may read.
TLSTerminated by the proxy (CF edge / Tailscale / Caddy auto-LE). Hub speaks plain HTTP on loopback to the proxy only.
session / cookieProxy issues and owns the session (CF_Authorization / Tailscale / oauth2-proxy). Hub sees only the trusted forwarded identity header per request — stateless about sessions.
CSRFKeep the existing Host + same-origin Origin check on POST (#233). With the public surface read-only, the CSRF surface shrinks to whatever writes are later exposed; those should add a custom-header/double-submit token if they ever ship.
authorizationRead-only publicly; writes stay loopback/trusted-LAN (C3). Hub maps forwarded identity → {read, denied}. The allowlist of who-may-read lives in the proxy's policy, not hub code.
secretsMinimal. Hub holds no IdP secrets (proxy does). The allowlist is a public list of identifiers, not a secret. TLS keys live with the proxy. If shoo is used later, its verifier keys are JWKS-fetched (public) — no shared secret crosses into the hub.
reverse proxyHub binds 127.0.0.1 only; proxy is the sole public listener and overwrites the identity header. Origin never directly reachable.
data exposureShip a redacted /summary.json (or restrict /data.json) before public serve is enabled, per C2.
Recommendation
Rec B. A read-only, loopback-bound hub fronted by a mature authenticating reverse proxy (Cloudflare Access or Tailscale Funnel first) that owns TLS, identity and the session, with the operator's authorisation allowlist at the proxy. Ship a redacted /summary.json. Serve no write route publicly.

Two-sentence version for the coordinator's report: a public Dreamhub should be a read-only, loopback-bound hub behind a mature authenticating reverse proxy that owns TLS, identity and the session; shoo.dev is an interesting Google-only identity primitive but is too early-stage, too trust-concentrating, and — because the stdlib-only hub cannot verify its ES256 tokens in-process — the wrong sole boundary for an agent control plane.

Open questions for the human — verbatim, for the coordinator to file
  1. Public or private remote? Is the real goal public access (any browser, anywhere, with auth) or private remote access (your devices only)? If the latter, Tailscale/WireGuard (option C) is strictly safer and "public" is not needed. This single answer rewrites the rest of the design.
  2. Is one reverse-proxy component acceptable? Cloudflare Access, Tailscale Funnel, or Caddy — given it keeps the hub itself stdlib-only and adds no auth code? If the hub itself must do auth, the design changes substantially and shoo-direct or a hosted IdP re-enters scope.
  3. Read-only, or read+write? This design recommends read-only publicly. Confirm, or name which write routes you would want exposed and under what extra guard.
  4. Identity provider choice. Shoo is Google-only and pre-release; CF Access / Tailscale / oauth2-proxy support Google, GitHub, email OTP, SAML, etc. Which IdP(s), and are you willing to depend on a Google account?
  5. May a redacted /summary.json be designed and shipped (separate task) before any public serve is enabled? Current /data.json leaks full DREAMWORK.md/questions.md/lessons.md and is unfit for public exposure as-is.
  6. Who, besides you, should ever reach this hub? Defines the authorisation allowlist and whether multi-identity is worth any complexity.
