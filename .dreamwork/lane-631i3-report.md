## How the oracle is independent of the scanner (Direction 2)

The brief's Direction 2 names the exact tautology to avoid: an ordered-stream
assertion over a frozen transcript passes vacuously if the oracle was
generated by the code under test. The #645 sibling work demonstrated and
printed this as FALSE GREEN.

My oracle is hand-authored. `_expected_frozen_events()` returns a literal
list of 15 `(ev_type, SessionNode(...))` tuples, each constructed by hand
from the §2/§3 tree-building rules — not by calling `scan_complete`. The
byte positions in each node's `SourceRef` are computed by `_byte_offsets`,
which is pure string arithmetic (`enumerate` + cumulative `len` + `+1` for
newline) — it calls no scanner function, does no JSON parsing, does no
classification. I verified this with AST call-graph analysis: the four
oracle helpers (`_byte_offsets`, `_ref`, `_expected_frozen_events`,
`_expected_frozen_bookmarks`) make **zero calls** to `scan_complete`,
`classify_record`, or `_iter_records`. The oracle is structurally incapable
of tautology.

### Direction 2: the false-green trap

The tautology trap is closed: the oracle is hand-authored and its helpers
make zero scanner calls (verified by AST). But I also looked for a
constructable false-green in the assertions themselves:

- The frozen oracle test (`test_frozen_transcript_complete_ordered_wire_stream`)
  compares `actual.node == node_exp` for each event — if `SessionNode.__eq__`
  were broken (e.g. comparing only `id`), a wrong-state or wrong-parent node
  would pass. But `SessionNode` is a `@dataclass(frozen=True)`, so `__eq__`
  is generated by the dataclass machinery and compares all fields. This is
  not a constructable false-green.

- The bookmark test (`test_tool_result_is_not_bookmarked`) asserts
  `"step.tool" not in bm_kinds` AND `len(result.bookmarks) == 4`. If only
  the length were checked, a tool-result bookmark replacing a legitimate
  one would pass. The kind-membership assertion closes that.

**Open false-green I cannot close:** the `examined` count asserts that the
scanner processed N lines, but it does not verify that those N lines were
the *right* lines — if `_iter_records` silently skipped a content line and
double-counted a chrome line, `examined` would still be 10. This is
structurally hard to close without a second independent line-counter, and
the frozen oracle's per-event `ref` assertions (which carry exact
line/byte positions independently computed by `_byte_offsets`) are what
catches a line-position drift in practice.

## DOGFOOD REPORT

**Friction found, stated.**

1. **The `_ScanState` refactor was forced by Python's closure semantics.**
   My first draft tried to pass `seq` as a mutable int through lambdas into
   helper functions (`lambda: seq`, `nonloc_refs()`), which is a classic
   Python footgun — you cannot mutate an int through a closure without
   `nonlocal`, and `nonlocal` does not compose with helper functions. The
   `_ScanState` class is the clean answer and should have been the first
   design, not the rescue. Cost: ~15 minutes of broken-code debugging that
   a moment of design would have prevented. This is a general Python
   pattern worth a one-line note in the design doc for the next lane that
   touches this file.
