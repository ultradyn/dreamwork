What approval decides

Nine questions, each with a recommendation, at the foot of this page. The three that change the shape rather than the detail: Q1 does the goal tree replace the session goal; Q2 does one refuter's refusal sink a completion, or does the panel vote; Q3 when the panel cannot run at all, does the goal complete or stall?

Question 1 · Where goals are stored

The ledger, as task_group rows with kind='goal'. Not a file, not a table of its own, not a second store. The reason is not doctrine — it is that v005_hierarchy already built the goal tree while it was building something else, and said so in its own docstring about the batch kind:

"an open vocabulary plus arbitrary depth makes a seed row rather than a table of its own" — dreamwork_db/migrations/v005_hierarchy.py:43

That sentence was written about batch. It describes goal exactly. What v005 shipped, and what each piece does for this feature:

already in the storewhat it gives the goal tree
task_group_kind (FK lookup, seeds lane epic milestone feature batch)one INSERT adds goal. No CHECK to rewrite — v005 removed the inline one for this reason
task_group.parent_id (adjacency, cycles refused at write time)the tree. Depth is data; a subgoal is a child row
task_group_memberbinds tasks to a leaf goal — the join where your hours meet the loop's minutes
task_group_dependency (at least one group endpoint)"this branch is blocked on that one", as an edge rather than prose
GroupRepository.blockers()every unmet prerequisite of a node including inherited ones — a subgoal inherits its parent's blocks free
GroupRepository.ready_tasks()open subtree tasks with nothing unmet. This is the branch-switching primitive, already written
GroupRepository.progress()subtree rollup, de-duplicated by task identity, and it refuses rather than returns zero — see the panel section

So v007_goals is small. Three additions, and only the first is interesting:

-- 1. Goals need a state the member tasks cannot derive. A goal is complete
--    when the PANEL says so, never because its tasks all landed — that is the
--    whole point of the gate, so it cannot be a derived column.
CREATE TABLE goal_state_kind (state TEXT PRIMARY KEY);   -- open claimed complete blocked
ALTER TABLE task_group ADD COLUMN goal_state TEXT REFERENCES goal_state_kind(state);

-- 2. The completion claim and every verdict against it. Append-only: a goal
--    refuted twice keeps both rounds, because round 2 must read round 1's gaps.
CREATE TABLE goal_claim (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    group_id      INTEGER NOT NULL REFERENCES task_group(id) ON DELETE CASCADE,
    claimed_by    TEXT    NOT NULL,
    claimed_at    TEXT    NOT NULL,
    summary       TEXT    NOT NULL,
    base_sha      TEXT,               -- NULL renders as `(unavailable)`, never as clean
    details_sha   TEXT    NOT NULL,   -- which version of the contract was claimed against
    outcome       TEXT,               -- NULL while in flight; complete | refuted | unrun
    round         INTEGER NOT NULL
);

CREATE TABLE goal_verdict (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    claim_id      INTEGER NOT NULL REFERENCES goal_claim(id) ON DELETE CASCADE,
    lens          TEXT    NOT NULL,   -- criteria | evidence | use
    refuted       INTEGER NOT NULL CHECK (refuted IN (0, 1)),
    blocking      TEXT    NOT NULL DEFAULT 'none',
    findings      TEXT    NOT NULL,   -- JSON array, grok's shape
    corroborated  TEXT    NOT NULL,   -- JSON array; EMPTY on a pass is malformed, not a pass
    examined      TEXT    NOT NULL    -- JSON: {criteria: n, members: n} — the precondition
);

-- 3. Which goal is current. A pointer, not a column, so exactly one row can
--    hold it and a stale second `current` is unrepresentable.
INSERT INTO meta (key, value) VALUES ('current_goal_id', '');

The details you edit are task_group.description, which exists, is TEXT NOT NULL DEFAULT '', and is empty on every current row. Adding a parallel details column would be a second body for one thing.

What this does not do: it does not touch the 730 task rows, does not change depends, and does not create a second place a goal can live. #850 is moving questions into this same store for the same reason; this arrives already inside it.

Question 3 · A details edit must reach the loop without notifying it

Your words: "An update to the details shouldn't notify the agent. It should just appear in the next main loop tick." That is the batched class from the delivery-modes ruling — except that the existing classes do not quite cover it, and the gap is one line.

PREEMPT_KINDS = ("chat", "do-now", "do-next")

def emits_wake(kind, target):
    if kind in PREEMPT_KINDS:
        return True
    return delivery_mode(target) == DELIVERY_DEFAULT   # DELIVERY_DEFAULT == "instant"

delivery is instant when the posture file is absent, which is the standing default. So under today's default, a goal-details edit would wake the loop — the ruled batched class only suppresses the wake when you have explicitly set delivery: batched. Your requirement was unconditional.

The minimal correct change is the mirror of PREEMPT_KINDS at the other end of the same axis — a QUIET_KINDS set consulted before the posture, so a quiet kind never wakes under any posture. This is not a parallel mechanism; it is the same predicate, made symmetric.

And it composes with #864, which is concurrently adding an expedited class between batched and instant. The four positions are ordered and disjoint, so the two lanes do not collide:

quiet never wakes, any posture — goal details (this task)
batched wakes only in instant mode — add-idea, answers, notes (ruled)
expedited never interrupts, drains at the next natural pause — #864
pre-empt wakes regardless — chat, do-now, do-next (ruled)

This design references those classes and does not rewrite delivery-modes.md; the row belongs there, added by whichever of #862/#864 lands second.

Question 4 · What a blocked branch does to selection

Almost nothing new, because the store already names the candidates and the selection algorithm already knows what to do with an empty answer.

A branch is blocked when it carries a task_group_dependency edge to something unmet, or you mark it blocked. blockers() returns unmet prerequisites including inherited ones, so a subgoal is blocked by its parent's blocker without any edge of its own.
The loop switches branches when ready_tasks(current_goal) comes back empty and some sibling's does not. ready_tasks's own docstring already draws the line: it "names the candidates honestly", and "WHICH candidates form a batch, and how many, is selection policy and lives in the loop." So this is one clause in SKILL.md step 0, not new code.
Every branch blocked falls through to today's behaviour verbatim — step 4 already says "A non-empty queue whose remaining tasks are all blocked is idle too — do not spend ticks reconsidering work that cannot start." The maintenance rotation runs.
But it says so loudly. An all-blocked goal tree is the #673 drift in a different dress — a loop rotating maintenance for six hours while every goal is stuck. So the tick line renders goal #G7 ALL BRANCHES BLOCKED (3 goals, 0 ready), and a question parks in questions.md on the first tick that finds it.
Question 5 · 2–12 hours against a 15–20 minute cap

These are different units and they do not convert. The task cap is a commit cadence — SKILL.md's tick asks "Past the ~20-minute cap? Land a coherent point, commit, split the remainder into a new task." A leaf goal is a deliverable. They meet at exactly one place: task_group_member.

6tasks in a 2-hour leaf, at the 20-minute cap
48tasks in a 12-hour leaf, at the 15-minute cap
24the proposed ceiling — past it, it is not a leaf
0live ledger entries carrying a stored size — so the band is counted, not measured

Forty-eight is too many to be one node, and printing the number is the argument for a rule rather than a guideline:

A leaf goal is 6–24 member tasks. A leaf that grows past 24 is re-parented, not re-estimated: it becomes a parent, its overflow moves into a new child subgoal, and its existing members stay attached where they are. That is the answer to "what happens when a leaf turns out to be 40 hours" — the tree absorbs it, and nothing has to be re-planned from scratch.

Who decomposes: the coordinator files subgoals; a dreamer may only propose them. The scope gate already makes the coordinator name the chain before adding new surface — "this task serves that session goal, which serves that goal in DREAMWORK.md" — and a goal node is that middle link. Handing goal creation to a lane inverts the gate that exists to catch invented links.

Measured, and it corrects a document. SKILL.md's task-list conventions say the ledger carries "size (estimated minutes)". It does not: there is no size column in any migration, no size in dreamwork_db/tasks.py or ledger_parse.py, and zero entries in the live ledger carry one. So the 2–12 hour band cannot be checked in minutes today, and this design deliberately states the leaf band in task count — which progress() does derive — rather than in a unit nothing stores. Adding a real size column is a separate task and this feature does not need it.
Question 6 · The refutation gate

This is the part you cannot get from the existing pieces, and the part where a mistake marks real goals complete. Four sub-questions: what a refuter is given, what makes them independent, what counts as refutation, and what stops a refuter passing a goal it never read.

What is handed to a refuter

Grok's input list, mapped onto artifacts this loop already produces. The right-hand column is why each one exists — a refuter given only the claim can only rubber-stamp it.

grok inputourswhat it is for
OBJECTIVEthe goal's title + details, at the details_sha the claim was made againstthe immutable contract
PLAN_FILEthe details' ## Done when — numbered criteriathe derived checklist it judges each item against
PLAN_CHANGESthe diff of the details since creation, with the actor of each edita criterion weakened by the loop is itself a finding
CHANGES_FILEgit diff over the member tasks' landing shasscope pointer and honesty anchor — not the sole evidence
CHANGED_FILESfiles those shas touched; it reads their current contentsthe workspace as it is now, not as the diff described it
FINAL_RESPONSEthe claim summaryclaims to attack. Prose is not evidence
PRIOR_GAPSround n−1's findingsthe anti-ratchet: round 2's primary job is checking these are fixed
— (ours)the member tasks' hand-off lines and lane reportsevery task here lands with its shas and both red-proof directions already written down
That last row is why this gate is cheap for us and expensive for grok. Grok's verifier hunts for the implementer's captured evidence in a scratch directory. Ours is already durable and already structured — the hand-off line names the shas, and the lane's report names the discriminating failure message its red-proof produced. The refuter audits a record that exists rather than reconstructing one.
Three refuters, three lenses — the independence is in the question, not the count

Grok runs three copies of one prompt. Three identical refuters are one refuter run three times: they share a blind spot and the majority hides it. Ours differ in what they are asked, and each catches a class the others structurally cannot:

L1 · criteria — did it meet the stated standard? Walks ## Done when item by item against the shas, citing path:line per item. Catches a missed or half-done criterion.
L2 · evidence — is the proof real? Audits each member task's red-proof: did a check ever go red on a discriminating message, was redproof.py check quoted, is any test hollow by this repo's three documented shapes (born hollow, become hollow, green red-run)? Catches a criterion that is met on paper by a check that could never fail.
L3 · use — does it actually work for you? Runs the thing on the real path: opens the route, invokes the verb, reads the pixels. Catches a feature that satisfies every criterion and is unusable.

Independence is then enforced three ways, all of which already exist here: at least one refuter on a different provider (a ccc lane, not another Claude) because a same-model panel shares priors; a lane-private scratch each (dev/lane_scratch.py, the #652 rule — grok hit the same collision and gave each skeptic its own dir); and no refuter sees another's verdict within a round.

What counts as a refutation, and who adjudicates a split

Any one lens refutes ⇒ refuted. Unanimity to pass. This is the divergence from grok worth arguing, because grok is deliberate about the opposite:

grok strict majority of the cold panel (skeptic 0, which shares the implementer's lineage, is excluded from the count but its refute still registers). Rationale in its own comment: "a lone outlier in either direction — one rubber-stamp or one false-refute — cannot decide the outcome."
ours any refute sinks it. Grok's three skeptics are interchangeable, so a lone dissent is noise. Our three are asked different questions, so a lone dissent is the only report from the lens that saw it — L1 and L3 cannot outvote L2 on a hollow check, because they never looked at one.

This repo's own history is the second argument. Three distinct false-green shapes are documented in CLAUDE.md, and its standing rule is "a green red-run is a finding, never a relief." A majority rule is a mechanism for discounting a minority finding; adopting one in a codebase whose stated lesson is that the minority finding is usually right would be the wrong default. The cost is more false refutes — paid for by adopting grok's anti-ratchet verbatim: on round ≥2 the panel's primary job is checking prior gaps are fixed, and a new objection is grounds only when it is a demonstrable defect or an unmet gating criterion, never a fresh preference.

The false green: what stops a refuter passing a goal it never examined

This is the highest-stakes vacuous green on the page, because its output marks real goals complete. Three layers, and the first one already exists.

The store refuses before the panel spawns. progress() raises EmptyGroup — "cannot judge progress for {kind} #{id}: 0 member tasks anywhere in its subtree ({n} group(s))" — and names how much subtree it examined. So a goal with no member tasks cannot be claimed, let alone passed. Extend it by one clause: the claim verb also refuses when every member is still open.
A pass must cite, and an uncited pass is malformed rather than a pass. Every not refuted verdict carries a corroborated array with one entry per criterion, each citing a sha, a path:line, or a captured run. An empty array on a pass is a malformed verdict — and malformed degrades to refuted: true, at the refuter, not at the aggregator. That placement is grok's and it is deliberate: "the aggregator counts votes; the bias lives upstream where the missing evidence is."
The panel asserts its own precondition. Each verdict records examined: {criteria: n, members: n}, and a round where either is 0 is reported as DID NOT JUDGE — not as a pass. This is the same distinction dev/ledger.py sweep makes with DID NOT REVIEW and tick_line._fleet_fact makes by raising when the probe examined zero processes. It is this repo's companion rule applied to the panel: assert in the check the precondition the check depends on.
Fail closed — the second divergence from grok

Grok fails open: a spawn error, a file-write failure or a status change during the spawn lets the completion through (GoalClassifierFailOpenReason). That is right for an interactive tool with a human watching the screen. It is wrong here — the dreamworker runs unattended for hours, and DREAMWORK.md's stated philosophy is that the loop "prefers a loud wrong state to a quiet one."

A panel that cannot run leaves the goal in claimed, records outcome: unrun with the reason, and the tick line says goal #G7 CLAIMED — PANEL UNRUN (spawn refused). The cost is a goal that sits claimed until someone looks. The benefit is that no goal is ever marked complete by an infrastructure failure.
What happens on refutation

Grok inlines the gaps into its implementer's next nudge. We do not have one implementer session — we have a queue, so findings become work:

round 1–2

Each finding files a task — origin: loop, parented to the goal node, priority inherited. The loop picks them up by ordinary selection. No special path, and no separate to-do list only the panel can see.

stall

Two rounds with the same finding fingerprints ⇒ the goal moves to blocked, reason no-progress, and parks a question. Grok's stall threshold is 2, for the same reason: identical gaps twice means iterating further is futile.

not a retry

Grok's blocking classes carry straight over. contradiction (the goal precludes itself) and unverifiable (no honest evidence path exists here) are decisions for you, not another round — so both park a question immediately instead of filing tasks.

cap

Three panels per goal, then it stops and asks. Grok's cap is 10, but its rounds are cheap and automatic; ours file real tasks that cost real lanes.

What it costs

Three refuters, each reading a goal, its details, its members' commits, and doing cheap spot-checks — roughly a small lane each, so one panel ≈ one ordinary lane's cost. With the three-round cap, a goal completion costs at most about three lanes. Against a leaf of 6–24 tasks that is roughly 4–15% overhead, worst case at the small end.

The ratio is the argument, and it only works at this altitude. The panel is per goal, not per task. Run per task it would cost more than the work; run per goal it is a rounding error against 6–24 tasks, and it is the only gate standing between "the agent said it was done" and "it is done."
The dashboard line and /dw-goals

You asked for the title on the project dashboard, clicking through to a /dw-goals page listing the goal and its details.

Dashboard — one row in the status region, above the fold: state chip, title, progress (7/19), and the blocked count when non-zero. The whole row is the link. Nothing else about goals renders here.
/dw-goals — the current goal in full (details rendered, criteria as a checklist, member tasks with states, blockers by name), then the tree: ancestors above, siblings beside, subgoals below. Then the last panel verdict with its findings per lens, because that is what you will want when a goal is stuck. The details are editable in place; the state is not — the panel owns complete.

Both transitions obey transitions.md, with no new idiom. Clicking the dashboard row is the route change, which is the reference implementation. The state chip changing and the goal row appearing when a first goal is set are smaller instances of the same gesture and reuse it — this repo's one rule with no exceptions, and it applies to a chip exactly as much as to a page.

One asymmetry worth stating, because grok gets it for free and we do not. Grok treats a weakened criterion as grounds to refute, because there only the agent can edit the plan. Here you can too, and when you weaken a criterion that is not a defect — it is the new contract. The store knows which, because every details edit carries its actor. So: weakened by the loop ⇒ a finding; weakened by you ⇒ the contract.

The session goal and DREAMWORK.md — how the three relate

There is already a session goal, in status.json, and standing goals in DREAMWORK.md. Leaving all three undefined against each other is the main way this design could go wrong, so: the goal tree is the middle rung, and it replaces the session goal.

DREAMWORK.md

Unchanged. Standing goals, prose, yours, outliving every session. The tree's roots each name a heading here, which is how the chain still terminates at something you wrote.

the goal tree

What the session goal already was — made durable, plural and tree-shaped. The scope gate's middle link ("this task serves that session goal, which serves that goal in DREAMWORK.md") becomes a goal node id instead of a string in a JSON file nothing can query.

The nine open questions

Each carries a recommendation. Ruling on none of them is the same as ruling on none of the page — nothing gets built either way.

Q1 · Does the goal tree replace the session goal? rec: yes. status.json.session_goal becomes derived and status-sync starts writing it. Needs your nod because SKILL.md currently forbids exactly that.
Q2 · One refuter's refusal, or a majority? rec: any one refutes. Our three lenses are not interchangeable, so a lone dissent is signal rather than noise. Grok votes because its three are identical. Cost: more false refutes, bounded by the anti-ratchet rule.
Q3 · When the panel cannot run at all? rec: fail closed — goal stays claimed, loudly. Diverges from grok deliberately: it has a human watching, we run unattended.
Q4 · Is the leaf band 6–24 tasks? rec: yes. Your 2–12 hours converted by commit cadence, not measured — nothing stores task size today. Past 24 the leaf is re-parented, not re-estimated.
Q5 · /dw-goals or /goals? rec: your literal /dw-goals. Every other route here is bare (/tasks, /questions), so it will look odd — but the prefix earns its keep in a hub aggregating several projects. Say the word and it is /goals.
Q6 · May you force-complete, bypassing the panel? rec: yes — you are the principal — and the claim records that it bypassed, so the history never reads as though a panel passed it.
Q7 · One current goal, or one per unblocked branch? rec: one. The tree already holds the alternatives, and two current goals is two answers to "what is the loop doing" — the shape this repo keeps paying for.
Q8 · Is the quiet delivery class acceptable? rec: yes. It is one QUIET_KINDS membership test before the posture read. Your requirement was unconditional, and the ruled batched class is conditional on a posture you have not set.
Q9 · Does blocked-ness reopen #95's D2? rec: yes, narrowly. #95 deferred branch focus until drift proved real and your request is that drift. But only blocked-ness steers — nothing forbids off-branch work, so the pottering character D2 protected is intact.
What approval means, and what it does not
Approving accepts the storage decision, the tick-line budget, the quiet delivery class, the leaf band, the three-lens panel and its two divergences from grok, and the nine recommendations you do not overrule. It does not authorise a migration, a route, a client view, or a panel run — the first increment under this id is v007_goals plus its red-first fixtures, each naming the production line that must change for it to fail. This branch contains no implementation: one source file, one built artifact, nothing else.
