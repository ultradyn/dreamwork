## The thing worth carrying: three of my own guards were wrong in the same way

Not wrong about the page — wrong about *themselves*. Each contained a check
that could not fail for the reason its message named:

- **`draft.mjs`'s #162(b) phase ran straight after a reload**, so its "the live
  text survived the mode switch" assertion was really re-testing the *restore*.
  On a build where only the restore was missing it would have reported the
  mode-switch path as broken — sending the next reader to the wrong file with a
  confident message.
- **`subslog.mjs`'s partition check rebuilt the expected database name inside
  the guard**, so it passed against a build with no store at all. It now calls
  the page's own `subsDbName`.
- **`subslog.mjs`'s "ids are monotonic" was `every` over an empty array**,
  which is `true`. The vacuous-loop trap again, one day after I wrote a lesson
  about it.

All three were invisible while green and invisible while *counted*. They only
showed up reading the red output line by line. Which is the rule:

**A check earns its message only if you have seen it fail for that message's
reason.** "It went red when I broke the feature" is not enough when one break
reddens twelve checks — the question is whether *this* check reddens for *its*
stated cause.

## A count is not evidence

I nearly reported "6 FAILs" for #175's red run. The real figure was 14. The 6
came from a `grep -c` in a compound command where the server had already been
swapped underneath it. I caught it only because 6 was implausibly *lower* than
the 11 I had seen minutes earlier.

Same shape as `prominence`'s `at(950)` earlier the same day: a convenient
number that was measuring something other than what it claimed. Read the
output; count afterwards if at all.

## Absence should cost one line, not thirty seconds

Three guards in this batch, on a build without the feature under test, waited
30s for a selector that would never appear and then reported *"the guard
threw"*. That message says nothing about the page and points at the guard.
`history.mjs` now asserts its subject exists first: absence is one FAIL with a
sentence, and the red run costs 3.4s. Worth generalising — it belongs with
#192.

## Two design notes that were arguments, not preferences

- **Browser storage was right for the draft and wrong for the tint (#143).** A
  tint is a setting *about* the project and should follow it to another
  machine, so it is a committable file. An unsent draft is a thought he has not
  chosen to send anyone; writing it into the repo would publish it.
- **The history's source changed under its own ledger line.** It proposed
  `watch-events.log`, written before #199 and #175 existed. `watch-events.log`
  is a rendering and cannot say whether a submission landed;
  `submissions.log` is verbatim but pre-outcome by construction; only the
  client log knows the outcome. Merging them would mean explaining, per row,
  which record it came from and what that record cannot tell him. A panel that
  apologises per row is worse than a narrow one that states its limit once.

## And one premise in the brief was wrong

#198 was briefed as "the end state is correct, so bound the window". The end
state is *not* correct — nothing autocorrects. What heals it is `setContent`
re-painting every group on the next view re-render, which his live dashboard
does every couple of seconds. **A wrong value that something else routinely
overwrites is not a transient; it is a permanent bug with a short, unreliable
lifetime.** The instruction to bound the window was right for the opposite
reason, and the guard proves the laundering path exists rather than trusting
it — because the fixture cannot re-render on its own, so a sloppy window would
have passed there by luck.
