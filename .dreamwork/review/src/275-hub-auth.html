IGC — no boundary passes all four goals, so the answer is an order

Method: igc-method.md (binary goals, ✔/✗/?, decisive error written out, never a score). The candidate boundaries for a self-hosted hub, judged on the four goals that actually discriminate here.

ssh tunnel ✗G3: the phone needs an ssh app and a reachable sshd off-LAN (Tailscale/WG mesh or a jump host) — recovered without a public port by a mesh, which is why it is the safest default. session key ✗G1: the #233 LAN bind is an inbound port on his machine — but it is loopback-or-LAN, fronted by a local Caddy, never a WAN listener. user/pw ✗G4: a sniffed/reused password over HTTP-on-LAN reaches the write routes unless TLS sits in front, and TLS fronting it makes user/pw redundant. hosted IdP ✗G2: the IdP’s control plane holds identity — the exact redirect #360 exists to make. SQRL ✗G3/G2-tech: dormant ecosystem, Ed25519 not in stdlib (the same wall that blocked shoo).

Survivor. No single idea passes all four. The ssh tunnel fails only G3 (phone convenience); the ssh session key fails only G1 (an already-chosen LAN bind). So the recommendation is not one boundary but an order: document the tunnel now (#360 §6, zero code); build the session key behind a local Caddy if the phone-without-ssh case is real. The three sub-decisions below are the ruling that gates both.

Q3 — read-only, or read+write, publicly?

Q3 — rec: read-only publicly. Writes stay loopback / trusted-LAN / ssh-tunnel. Measured, not preferred:

(a) The hub and the watch dashboard are different surfaces. dreamhub.py is a read-only aggregate — its handler serves only GET /hub.json, GET /rows and GET / (do_GET at dreamhub.py:831), writes nothing outside ~/.config/dreamwork/hub/, and has no do_POST. watch.py is the other surface: it carries six write routes (WRITE_ROUTE_HANDLERS, dispatched from do_POST at watch.py:11651) — /answer, /ask, /comment, /command, /tint, /run-mode — and every one appends to a durable file the loop reads back and acts on. /command with do-now is remote steering of an autonomous agent.

(b) A public write route is the #288 incident handed to the internet. #288 proved a same-UID process can kill a live protected service to satisfy an invented premise; #358’s framing names the boundary that matters — the body “can only kill itself”. A public /command makes the credential the head’s equal: a stolen session cookie points the agent at arbitrary work, up to commit / push / deploy. Read-only publicly bounds a compromised credential to data leak; read+write publicly bounds it to agent takeover. A v1 should not make that trade.

Q5 — may a redacted /summary.json ship before any public serve?

Q5 — rec: yes — it is the blocker for any non-loopback serve. The plan’s C2 says /data.json leaks full documents; verified against collect() (watch.py:10756) it is worse — the loop’s whole operating state, including his unfinished thinking:

  • Most sensitive — his words and private direction. files.questions.md (typed questions, answers, notes in full), files.DREAMWORK.md, files.lessons.md, questions_open/answered_entries (parsed bodies), answers_open/answers_answered (his channel to the loop), pending_handoffs, dreams/dreams_archive (transcripts).
  • Operational state — reveals pace and where it is blocked. status (full status.json: queue, current tasks, agent ownership, deployed pid), git, burndown, deployed.
  • Safe to expose. open_questions (a count), questions_health/answers_health, target, generated, tint, run_mode, posture, skill_identity.

A redacted /summary.json keeps the counts, health and metadata and drops every full-text and parsed-entry field. #360’s option 2 already carries it as a hard prerequisite; Q5 makes it a shippable task of its own, decoupled from the auth choice. A credential should not gate a route that then leaks questions.md in full.

Q6 — who besides you should ever reach this hub?

Q6 — rec: you only, for v1. The surface (even redacted) carries the loop’s working state, and any non-redacted path carries his questions, answers and transcripts — adding a second identity is a decision to share his private thinking, which is his. #360’s option 2 makes a second identity mechanically cheap (one ssh … issue-session per device, per-device revocable), so the allowlist needs no multi-identity code up front. Starting at “you only” widens later for one issue-command; starting wide leaks first and narrows by revocation. v1 single-operator also sidesteps the “whose data is this” question entirely.
