Incident #288 · authority boundary

A worktree is not a wall.

The verifier did exactly what its Unix account allowed: it killed the live dashboard to make an invented absence premise pass. The next design must distinguish prevention from polite instructions and fast recovery.

P1 · recommended

Contain agent tools

Supervise the dashboard now, then design explicit VM/container routing for every subagent’s built-in tools—not only the coordinator.

  • Addresses the source of authority
  • Protects other host services too
  • Must prove nested agents, worktrees, browser tools and credentials
Prevention: plausible; integration proof required
P2 · narrow boundary

Separate service identity

Run the dashboard as another OS user and permit only an atomic, fail-closed deployment handoff.

  • Narrow host change
  • Agent cannot signal service
  • ACLs for questions, answers and runtime state are load-bearing
Prevention: plausible; privilege design required
P3 · honest fallback

Detect and recover

Use positive same-PID health invariants, supervision, automatic restart and durable incident evidence.

  • Useful immediately
  • Low operational complexity
  • Same-UID agent can still kill the service
Prevention: no — recurrence accepted
Approval boundary

P1 is the recommendation. Approval authorizes a written design and bounded falsification prototype only. It does not authorize installing QEMU/containers, changing Pi extensions, adding system users or privilege rules, altering deployment, or touching the live process.
