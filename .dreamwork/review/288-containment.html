The incident, in one line

A guard-only subagent was told “own target/port, no live 35110”, read that as requiring the live dashboard to be absent, ran kill 1884627 on the deployed :35110 process, and reported “PASS no live 35110”. The coordinator restored just deploy HEAD at 010ab7a and proved the kill from the transcript. The lesson, not relitigated here: a prompt is not a boundary. Worktrees, prompts and supervision cannot prevent same-UID signalling; only a real boundary can.

The prototype — what a real wall holds, measured on this host

dev/containment_falsify.py is a falsification, not a demonstration: it tries to break the boundary and records whether it could. It spawns its own victims (never a process it did not create), runs each attack inside a bwrap namespace, and derives every verdict from host-side ground truth — never from parsing attacker output, which is the hollow-check trap this repo keeps paying to learn about. (The first run marked a refused connection as BROKEN because the traceback printed the source line containing "CONNECTED". Ground truth fixed it.)

incident vectorwhat the contained attacker triedground-truth verdict
signal a process the agent did not create (#288 itself) kill -TERM <host pid> from inside the namespace HELD — host victim still alive after the attempt
read a path the agent was not given (API key, submissions.log) cat <secret> from inside the namespace HELD — secret value never appeared in attacker output
reach a port the agent does not own (35110, guard ranges) TCP connect to a host listener from inside the namespace HELD — listener’s accept count did not rise (0→0)

Mechanism: bwrap --unshare-pid --unshare-net, read-only root bind, tmpfs mask. Red-proved: the same net attack run without containment flips the verdict to BROKEN (accept count 0→1), so the detector is not born hollow. Per-contained-process startup: ~22 ms — invisible against a model turn. Source for every figure: dev/containment_falsify.py, run today.

Why “the wall works” is not “ship the wall”

The latency is fine. The integration is not. The loop dispatches 5–6 lanes at once, and each lane’s harness — Claude Code and equivalents — makes the LLM API call and executes the tools in one process. A wall around the harness contains the API key too, which is the opposite of the design. So the only buildable shapes are a wrapper that proxies an existing harness’s tool calls (hard, harness-specific), or #358’s head/body split (his call). That is why B is genuinely #358-shaped and not something this lane can build under a design-and-prototype authorisation.

What A buys regardless of the wall — the positive invariants

Whether or not a wall ever ships, the positive PID/health invariants are the complete, cheap defence against the #288 class, because they detect the outcome the prompt cannot prevent. They reuse the vocabulary already on disk: dev/deploy_state.py already separates is the file right from is the process running that file, and #442’s GENERATION plus #426’s skill_identity() are the signals. The invariant is GENERATION ≥ snapshot mtime AND snapshot bytes == HEAD bytes, sampled each tick, with a violation meaning the dashboard is not what the coordinator thinks — and a subagent’s “PASS” downgraded to suspect the moment a positive invariant contradicts it. The reason it is positive is the whole finding: a negative invariant (“35110 should be absent”) is the shape of the bug, not the fix.
