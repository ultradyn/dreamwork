# 2026-07-25 — durable task ledger

## What changed

**The ledger** — the queue's durable record, holding open tasks and
their **permanent ids**. A session-scoped backend empties on restart and
takes its ids with it, breaking every reference in docs, questions,
dreams, and commit messages. So: where the backend already survives a
restart (`bl`) it *is* the ledger; where it doesn't (the native tools),
`.dreamwork/tasks.md` is, and initialization restores the backend from
it before judging the queue. Each task wears its id at the front of its
subject — the one field every backend reads back.

Found by dogfooding: restarting the skill's own session dropped a queue
of eight tasks whose ids were referenced across four documents.

## How to apply

Skip entirely on a backend with durable ids of its own (`bl`) — that
backend is already the ledger.

Otherwise apply at **step 8 (reconcile), not step 7**: the update check
runs while a session-scoped backend is still empty, so building the
ledger "from the current open tasks" there would silently bless an empty
queue. Reconstruct instead from what is durable — the git log, plans
under `.dreamwork/docs/plans/`, open entries in `questions.md`, handoff
docs — and write `.dreamwork/tasks.md`: one line per open task with id,
title, priority/type/size, owner or blocked-on, a pointer to any
plan, and — for started tasks — its goal and parent (see migration
2026-07-25-12). Ids continue from the highest ever used on that target (never
reused); the file records the next one. Put each id at the front of its
task's subject — the backend's own numbering stays session-local, and
its `metadata` may never be readable.

From then on the coordinator — and only the coordinator — rewrites the
ledger, in the same commit as the queue change (reflection checklist
step 5).
