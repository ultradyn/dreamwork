Design call 1 · Where goals are stored

The ledger, as task_group rows with kind='goal'. Not a file, not a table of its own, not a second store. The reason is not doctrine — it is that v005_hierarchy already built the goal tree while it was building something else, and said so in its own docstring about the batch kind:

"an open vocabulary plus arbitrary depth makes a seed row rather than a table of its own" — dreamwork_db/migrations/v005_hierarchy.py:43

That sentence was written about batch. It describes goal exactly. What v005 shipped, and what each piece does for this feature:

already in the storewhat it gives the goal tree
task_group_kind (FK lookup, seeds lane epic milestone feature batch)one INSERT adds goal — v005 removed the inline CHECK
task_group.parent_id (adjacency, cycles refused at write time)the tree. Depth is data; a subgoal is a child row

So v007_goals is small. Four additions — the first is the interesting one, and the fourth is the one your Q7 ruling requires:

-- 1. Goals need a state the member tasks cannot derive. A goal is complete
--    when the PANEL says so, never because its tasks all landed — that is the
--    whole point of the gate, so it cannot be a derived column.
CREATE TABLE goal_state_kind (state TEXT PRIMARY KEY);   -- open claimed complete blocked
ALTER TABLE task_group ADD COLUMN goal_state TEXT REFERENCES goal_state_kind(state);

-- 2. The completion claim and every verdict against it. Append-only: a goal
--    refuted twice keeps both rounds, because round 2 must read round 1's gaps.
CREATE TABLE goal_claim (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    group_id      INTEGER NOT NULL REFERENCES task_group(id) ON DELETE CASCADE,
    claimed_by    TEXT    NOT NULL,
    claimed_at    TEXT    NOT NULL,
    summary       TEXT    NOT NULL,
    base_sha      TEXT,               -- NULL renders as `(unavailable)`, never as clean
    details_sha   TEXT    NOT NULL,   -- which version of the contract was claimed against
    outcome       TEXT,               -- NULL while in flight; complete | refuted | unrun
    round         INTEGER NOT NULL
);

CREATE TABLE goal_verdict (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    claim_id      INTEGER NOT NULL REFERENCES goal_claim(id) ON DELETE CASCADE,
    lens          TEXT    NOT NULL,   -- criteria | evidence | use
    refuted       INTEGER NOT NULL CHECK (refuted IN (0, 1)),
    blocking      TEXT    NOT NULL DEFAULT 'none',
    findings      TEXT    NOT NULL,   -- JSON array; EVERY refutation found, not the first
    corroborated  TEXT    NOT NULL,   -- JSON array; EMPTY on a pass is malformed, not a pass
    examined      TEXT    NOT NULL    -- JSON: {criteria: n, members: n} — the precondition
);

-- 3. Which goal is current. A pointer, not a column, so exactly one row can
--    hold it and a stale second `current` is unrepresentable.
INSERT INTO meta (key, value) VALUES ('current_goal_id', '');

-- 4. Your Q7 ordering, which nothing today can express: `task_group` carries
--    no rank column of any kind, so "which unblocked branch does the fleet
--    fill next" has no answer except an arbitrary one. Sibling-scoped, so a
--    reorder rewrites one parent's children rather than the tree; a pre-order
--    walk by rank then yields a total order without storing one.
ALTER TABLE task_group ADD COLUMN goal_rank INTEGER;   -- NULL sorts last

The details you edit are task_group.description, which exists, is TEXT NOT NULL DEFAULT '', and is empty on every current row. Adding a parallel details column would be a second body for one thing.

What this does not do: it does not touch the 730 task rows, does not change depends, and does not create a second place a goal can live. #850 is moving questions into this same store for the same reason; this arrives already inside it.

Design call 3 · A details edit must reach the loop without notifying it

Your words: "An update to the details shouldn't notify the agent. It should just appear in the next main loop tick." That is the batched class from the delivery-modes ruling — except that the existing classes do not quite cover it, and the gap is one line.

PREEMPT_KINDS = ("chat", "do-now", "do-next")

def emits_wake(kind, target):
    if kind in PREEMPT_KINDS:
        return True
    return delivery_mode(target) == DELIVERY_DEFAULT   # DELIVERY_DEFAULT == "instant"

delivery is instant when the posture file is absent, which is the standing default. So under today's default, a goal-details edit would wake the loop — the ruled batched class only suppresses the wake when you have explicitly set delivery: batched. Your requirement was unconditional.

The minimal correct change is the mirror of PREEMPT_KINDS at the other end of the same axis — a QUIET_KINDS set consulted before the posture, so a quiet kind never wakes under any posture. This is not a parallel mechanism; it is the same predicate, made symmetric.

And it composes with #864, which is concurrently adding an expedited class between batched and instant. The four positions are ordered and disjoint, so the two lanes do not collide:

quietnever wakes, any posture — goal details (this task)
batchedwakes only in instant mode — add-idea, answers, notes (ruled)
expeditednever interrupts, drains at the next natural pause — #864
pre-emptwakes regardless — chat, do-now, do-next (ruled)

This design references those classes and does not rewrite delivery-modes.md; the row belongs there, added by whichever of #862/#864 lands second.

Design call 4 · What a blocked branch does to selection, and what orders the rest

Blocked-ness needs almost nothing new: the store already names the candidates and the selection algorithm already knows what to do with an empty answer. The ordering you added in Q7 is the one genuinely new thing here, because nothing in the store can express it today.

A branch is blocked when it carries a task_group_dependency edge to something unmet, or you mark it blocked. blockers() returns unmet prerequisites including inherited ones, so a subgoal is blocked by its parent's blocker without any edge of its own.
The loop switches branches when ready_tasks(current_goal) comes back empty and some sibling's does not. ready_tasks's own docstring already draws the line: it "names the candidates honestly", and "WHICH candidates form a batch, and how many, is selection policy and lives in the loop." So this is one clause in SKILL.md step 0, not new code.
The order decides which branch the fleet takes. Your words: "we should have a prioritization order of them so we can keep work parallelized." One current goal still answers what is the loop doing — that is Q7's rec, and it is unchanged. The ordering answers the different question a wide fleet asks: with several branches unblocked and lanes to spare, which do the other lanes take? Without it the coordinator picks arbitrarily, and arbitrary picks are how a fleet ends up spread across work that does not compose. So ready_tasks is walked in rank order; how many candidates become lanes stays selection policy, as above.
Every branch blocked falls through to today's behaviour verbatim — step 4 already says "A non-empty queue whose remaining tasks are all blocked is idle too — do not spend ticks reconsidering work that cannot start." The maintenance rotation runs.
But it says so loudly. An all-blocked goal tree is the #673 drift in a different dress — a loop rotating maintenance for six hours while every goal is stuck. So the tick line renders goal #G7 ALL BRANCHES BLOCKED (3 goals, 0 ready), and a question parks in questions.md on the first tick that finds it.
Design call 5 · Leaf size — Q4, overridden

The recommendation was a leaf of 6–24 member tasks, derived by converting your 2–12 hours against the loop's ~15–20 minute cap (2h/20min = 6, 12h/15min = 48, and 48 called too many for one node, so 24 became the ceiling). You rejected the derivation, and the reason matters more than the number:

"the 15-20 min cap is to keep the main agent able to effectively process new events. when using subagents we don't care so much. the leaf goal should have as many tasks as needed for sensible decomposition, and probably all tasks can be handled by one subagent at once unless there's a reason to break them up or doing so allows them to be parallelized (which is good where possible)." — you, 2026-08-01

The cap is about the coordinator's own event responsiveness: it exists so the main agent keeps processing what arrives, and a subagent doing the work is not subject to it. So it is not a statement about how large a unit of work may be — it says nothing about a task, and therefore nothing about a leaf, and it does not convert. This page had already written that these were different units that do not convert, one line before converting them; the ruling is that the first half was right and the conversion should never have followed it.

A leaf goal holds as many tasks as sensible decomposition needs, and what a split optimises for is parallelism. One subagent may take a whole leaf when there is no reason to break it up. Breaking it up is right when the pieces are genuinely independent — that is what lets them run at once, and running wide is the thing worth buying. No count replaces 6–24. A fresh band — 4–40, "about a dozen" — would be the same mistake wearing a new constant, and would re-impose a ceiling where the ruling put a judgement.

What the struck rule carried and the ruling keeps: your hours and the loop's minutes still meet at exactly one place, task_group_member; and a leaf that turns out far larger than expected is still absorbed by re-parenting rather than re-planning — it becomes a parent and its separable parts move into children, its existing members staying where they are. That is now a description of what decomposition does when the parts come apart, not a threshold that fires at 25.

Who decomposes: the coordinator files subgoals, a dreamer may only propose them — and you may add them directly (Q5). The scope gate already makes the coordinator name the chain before adding new surface — "this task serves that session goal, which serves that goal in DREAMWORK.md" — and a goal node is that middle link, so handing goal creation to a lane inverts the gate that exists to catch invented links. You are not subject to that gate: a goal you write is the top of a chain.

One measurement here survives the override untouched, because it was never part of the derivation. SKILL.md's task-list conventions say the ledger carries "size (estimated minutes)". It does not: there is no size column in any migration, no size in dreamwork_db/tasks.py or ledger_parse.py, and zero entries in the live ledger carry one. SKILL.md is wrong about its own store — and a leaf could not have been checked in hours or minutes even under the rule you struck. Correcting that sentence, or adding a real size column, is a separate task this feature does not need.
Design call 6 · The refutation gate

This is the part you cannot get from the existing pieces, and the part where a mistake marks real goals complete. Four sub-questions: what a refuter is given, what makes them independent, what counts as refutation, and what stops a refuter passing a goal it never read.

What is handed to a refuter

Grok's input list, mapped onto artifacts this loop already produces. The right-hand column is why each one exists — a refuter given only the claim can only rubber-stamp it.

grok inputourswhat it is for

That last row is why this gate is cheap for us and expensive for grok. Grok's verifier hunts for the implementer's captured evidence in a scratch directory. Ours is already durable and already structured — the hand-off line names the shas, and the lane's report names the discriminating failure message its red-proof produced. The refuter audits a record that exists rather than reconstructing one.
Three refuters, three lenses — the independence is in the question, not the count

Grok runs three copies of one prompt. Three identical refuters are one refuter run three times: they share a blind spot and the majority hides it. Ours differ in what they are asked, and each catches a class the others structurally cannot:

criteria — did it meet the stated standard? Walks ## Done when item by item against the shas, citing path:line per item. Catches a missed or half-done criterion.
evidence — is the proof real? Audits each member task's red-proof: did a check ever go red on a discriminating message, was redproof.py check quoted, is any test hollow by this repo's three documented shapes (born hollow, become hollow, green red-run)? Catches a criterion that is met on paper by a check that could never fail.
use — does it actually work for you? Runs the thing on the real path: opens the route, invokes the verb, reads the pixels. Catches a feature that satisfies every criterion and is unusable.
Each lens enumerates; it does not stop at its first hit. Your words: "these subagents should be told to come up with all the refutations they can, not just one or two. we want to get a good list to fix as much as possible at once." A refuter that finds one fatal problem and returns has done a third of its job — under "any one refutes" the outcome was already settled by that first finding, so everything it then stops looking for becomes a later round nobody needed. The lens brief therefore asks for a complete list within its own lens, and the verdict's findings array is that list.

Independence is then enforced three ways, all of which already exist here: at least one refuter on a different provider (a ccc lane, not another Claude) because a same-model panel shares priors; a lane-private scratch each (dev/lane_scratch.py, the #652 rule — grok hit the same collision and gave each skeptic its own dir); and no refuter sees another's verdict within a round.

What counts as a refutation, and who adjudicates a split

Any one lens refutes ⇒ refuted. Unanimity to pass. This is the divergence from grok worth arguing, because grok is deliberate about the opposite:

Ggrok votes. A strict majority of the cold panel — skeptic 0 shares the implementer's lineage, so it is excluded from the count though its refute still registers. Its rationale: "a lone outlier in either direction — one rubber-stamp or one false-refute — cannot decide the outcome."
Dours does not. Grok's three skeptics are interchangeable, so a lone dissent is noise. Ours are asked different questions, so a lone dissent is the only report from the lens that saw it — criteria and use cannot outvote evidence on a hollow check, because they never looked at one.

This repo's own history is the second argument. Three distinct false-green shapes are documented in CLAUDE.md, and its standing rule is "a green red-run is a finding, never a relief." A majority rule is a mechanism for discounting a minority finding; adopting one in a codebase whose stated lesson is that the minority finding is usually right would be the wrong default. The cost is more false refutes — paid for by adopting grok's anti-ratchet verbatim: on round ≥2 the panel's primary job is checking prior gaps are fixed, and a new objection is grounds only when it is a demonstrable defect or an unmet gating criterion, never a fresh preference.

So the boolean is only the gate; the list is the product. Whether the goal completes is decided by whether any lens refuted. What gets done is decided by everything all three found. A round that returns one refutation and a verdict has produced a correct gate and a poor product — the distinction your Q2 addition draws, and the reason the fix pass below works a batch rather than a blocker.

The false green: what stops a refuter passing a goal it never examined

This is the highest-stakes vacuous green on the page, because its output marks real goals complete. Three layers, and the first one already exists.

The store refuses before the panel spawns. progress() raises EmptyGroup — "cannot judge progress for {kind} #{id}: 0 member tasks anywhere in its subtree ({n} group(s))" — and names how much subtree it examined. So a goal with no member tasks cannot be claimed, let alone passed. Extend it by one clause: the claim verb also refuses when every member is still open.
A pass must cite, and an uncited pass is malformed rather than a pass. Every not refuted verdict carries a corroborated array with one entry per criterion, each citing a sha, a path:line, or a captured run. An empty array on a pass is a malformed verdict — and malformed degrades to refuted: true, at the refuter, not at the aggregator. That placement is grok's and it is deliberate: "the aggregator counts votes; the bias lives upstream where the missing evidence is."
The panel asserts its own precondition. Each verdict records examined: {criteria: n, members: n}, and a round where either is 0 is reported as DID NOT JUDGE — not as a pass. This is the same distinction dev/ledger.py sweep makes with DID NOT REVIEW and tick_line._fleet_fact makes by raising when the probe examined zero processes. It is this repo's companion rule applied to the panel: assert in the check the precondition the check depends on.
Fail closed — the second divergence from grok

Grok fails open: a spawn error, a file-write failure or a status change during the spawn lets the completion through (GoalClassifierFailOpenReason). That is right for an interactive tool with a human watching the screen. It is wrong here — the dreamworker runs unattended for hours, and DREAMWORK.md's stated philosophy is that the loop "prefers a loud wrong state to a quiet one."

A panel that cannot run leaves the goal in claimed, records outcome: unrun with the reason, and the tick line says goal #G7 CLAIMED — PANEL UNRUN (spawn refused). And it asks a human — your ruling was "rec + ask a human (may or may not block depending on context)", both rather than either. So a question parks carrying the reason, and whether the loop waits on the answer or moves to another branch is read from context rather than fixed here. Failing closed is the state, the ask is the escalation, and only the blocking is contextual. No goal is marked complete by an infrastructure failure, and none sits claimed in silence.
What happens on refutation

Grok inlines the gaps into its implementer's next nudge. We do not have one implementer session — we have a queue, so findings become work:

round 1–2

Evaluate, then fix the lot in one pass. Your instruction: "evaluate the claimed refutation and then address it by fixing all issues identified" — so a finding is itself a claim, and the first step is judging it rather than obeying it (grok names an invented requirement as the most common false refute, which is what ## Not in scope exists to kill). What survives becomes work: each finding files a task — origin: loop, parented to the goal node, priority inherited — and the round's whole surviving set is worked as one batch. The loop picks them up by ordinary selection; no special path, no separate to-do list only the panel can see. A finding the loop dismisses is recorded with its reason, because that is precisely what round 2 must be able to re-read.

stall

Two rounds with the same finding fingerprints ⇒ the goal moves to blocked, reason no-progress, and parks a question. Grok's stall threshold is 2, for the same reason: identical gaps twice means iterating further is futile.

not a retry

Grok's blocking classes carry straight over. contradiction (the goal precludes itself) and unverifiable (no honest evidence path exists here) are decisions for you, not another round — so both park a question immediately instead of filing tasks.

cap

Three panels per goal, then it stops and asks. Grok's cap is 10, but its rounds are cheap and automatic; ours file real tasks that cost real lanes.

What it costs

Three refuters, each reading a goal, its details, its members' commits, and doing cheap spot-checks — roughly a small lane each, so one panel ≈ one ordinary lane's cost. With the three-round cap, a goal completion costs at most about three lanes. With the leaf band struck, the overhead is a ratio rather than a quotable figure: three lanes over the leaf's own task count — about 15% for a leaf of six, about 6% for a leaf of twenty.

The ratio is the argument, and it only works at this altitude. The panel is per goal, not per task. Run per task it would cost more than the work it gates; run per goal it is small against any leaf worth calling one, and it is the only gate standing between "the agent said it was done" and "it is done."

The session goal and DREAMWORK.md — how the three relate

D2 is reopened on the trigger #95 itself named. It deferred branch focus with "add preference weights only if drift actually shows up" and "cheaper to add later than to unpick". D3 is not a reversal at all. Its argument against stable ids was specifically that they "add an id space to a file you edit by hand". Goal node ids live in the store; DREAMWORK.md keeps its free-text headings and its dangling-name check, both untouched.

What survives that licence is why they are named at all: a decision reversed silently is one nobody can audit later.

The character argument from D2 survives, and this design is built to keep it. #95 rejected enforcement partly because it "fights the loop's character: the free-flowing 'potter productively' quality comes partly from being allowed to pick up the adjacent thing." So what lands here is not a filter that forbids off-branch work. ready_tasks names candidates; it excludes nothing. The only thing that actually steers is blocked-ness — the loop leaves a branch it cannot progress. Pottering is untouched.
The nine questions, and how you ruled

Ruled 1 August 2026 via the dashboard. Each question is kept with the recommendation it carried and your answer beside it, so a reader in a month can see what was asked, what was proposed, and what was decided — including the one that was proposed and refused.

Q1 · Does the goal tree replace the session goal? rec: yes · ruled: rec. status.json.session_goal becomes derived and status-sync starts writing it, flipping the SKILL.md line that lists it among the fields a tool cannot derive.
Q2 · One refuter's refusal, or a majority? rec: any one refutes · ruled: rec, and widened. The gate stands. What changed is the refuter's job: "these subagents should be told to come up with all the refutations they can, not just one or two. we want to get a good list to fix as much as possible at once", then "evaluate the claimed refutation and then address it by fixing all issues identified." So a refuter enumerates rather than votes, and the panel's product is a fix list evaluated and worked in one pass — see the panel.
Q3 · When the panel cannot run at all? rec: fail closed · ruled: rec and ask a human — "(may or may not block depending on context)". Both, not either: the goal stays claimed, and a question parks with the reason; whether the loop waits on it is contextual.
Q4 · Is the leaf band 6–24 tasks? rec: yes · ruled: OVERRIDDEN. The rec derived 6–24 by converting your 2–12 hours against the ~15–20 minute cap. You rejected the derivation, not just the figure: "the 15-20 min cap is to keep the main agent able to effectively process new events. when using subagents we don't care so much. the leaf goal should have as many tasks as needed for sensible decomposition, and probably all tasks can be handled by one subagent at once unless there's a reason to break them up or doing so allows them to be parallelized (which is good where possible)." The cap governs the coordinator's event responsiveness and converts into nothing; decomposition governs the leaf, and parallelism is what a split buys. No replacement number was set, and none should be inferred — 6–24 is still printed here and in leaf size, marked, rather than quietly deleted, so nobody re-derives it.
Q5 · /dw-goals or /goals? rec: /dw-goals · ruled: /goals, plus a requirement. "/goals is fine, i just wanted to make it clear that it was dreamwork goals for the project rather that user goals, but it's kinda both i guess, the user should be able to add goals or conditions/details on goals." The prefix was marking ownership, not naming a route — and the tree is now your input surface as well as the loop's: the page.
Q6 · May you force-complete, bypassing the panel? rec: yes · ruled: rec. You are the principal, and the claim records that it bypassed, so the history never reads as though a panel passed it.
Q7 · One current goal, or one per unblocked branch? rec: one · ruled: rec, plus an ordering. "we should have a prioritization order of them so we can keep work parallelized." One current goal still answers what is the loop doing; the order answers what the rest of the fleet takes, which is the question a wide fleet asks and nothing in the store could answer — selection, and a rank column in the migration.
Q8 · Is the quiet delivery class acceptable? rec: yes · ruled: rec. One QUIET_KINDS membership test before the posture read. Your requirement was unconditional; the ruled batched class is conditional on a posture you have not set.
Q9 · Does blocked-ness reopen #95's D2? rec: yes, narrowly · ruled: rec, and licensed. "we can update the protocol from 95 however we like to fit our current and future needs." So the reversals are permitted outright rather than argued past — #95. Only blocked-ness steers; nothing forbids off-branch work.

One thing in the same answer is deliberately not designed here: "having subagent prompts pre-written alongside tasks might speed things up a lot … if we could just use a template to generate the prompt automatically."
