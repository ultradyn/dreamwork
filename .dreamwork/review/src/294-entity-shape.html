The two shapes, side by side

A — the landed split (50f4933): attributes on entry, permanent ids on task, every read joins the two.

CREATE TABLE entry (
  entry_id INTEGER PRIMARY KEY AUTOINCREMENT,
  state    TEXT NOT NULL CHECK (state IN ('open','landed')),
  title    TEXT NOT NULL,
  body     TEXT NOT NULL,
  priority TEXT REFERENCES priority_band(band),        -- nullable
  priority_uncertain INTEGER NOT NULL DEFAULT 0,
  type     TEXT REFERENCES task_type(type),
  origin   TEXT CHECK (origin IS NULL
             OR origin IN ('human','loop','unknown')),
  body_digest TEXT, source_line INTEGER
);
CREATE TABLE task (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  entry_id INTEGER NOT NULL REFERENCES entry(entry_id),
  ordinal  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX task_by_entry ON task(entry_id);

B — the flat entity (5c5e534, wt/294): one row per permanent id, every attribute on task, no join anywhere.

CREATE TABLE task (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  state    TEXT NOT NULL CHECK (state IN ('open','landed')),
  title    TEXT NOT NULL,
  body     TEXT NOT NULL,
  priority TEXT NOT NULL REFERENCES priority_band(band),
  priority_uncertain INTEGER NOT NULL DEFAULT 0,
  type     TEXT REFERENCES task_type(type),
  origin   TEXT NOT NULL
             CHECK (origin IN ('human','loop','unknown')),
  owner    TEXT,
  blocked_on TEXT,        -- verbatim prose, never an edge
  body_digest TEXT, source_line INTEGER
);
-- no entry table, no task_by_entry;
-- related / depends / review_decision / task_event /
-- task_state unchanged between the two

B bundles two strictness upgrades and two columns, all separable from the flatten itself: priority NOT NULL (the 6 bandless entries are #353's to resolve pre-import) and origin NOT NULL (absence below id 216 is derivable — S3 was withdrawn), plus owner and blocked_on as verbatim prose.

G3 is why this is asked today, not after the import. The #294 entry names the error: migrating into a schema that is then flattened is the two-migrations error. Before the import, flattening costs replacing a schema with no data and no consumer. After the import, the same change is a data migration over permanent ids — the exact double-migration you have warned about twice.
What each choice commits to — read this before ruling
A — keep the split. You commit every consumer to the join, permanently: #346's read verbs (list / get / count), the ?t= resolver, the import script, #264's write verbs, and the future Postgres port each carry the entry_id↔task-id mapping and a join that is always 1:1. You keep two id namespaces for one real one, and #346's finding-1 fixture ("get 138 and 156 return one body") keeps protecting a case reality no longer contains. Because flattening after import is the two-migrations error, A is not "split for now" — it is "split forever".
B — flatten. You commit to replacing increment 1's entity shape with 5c5e534 before the import stage — free today, because 50f4933 has no production consumer, no data, and no cutover; its 14 tests are superseded by 1b's suite. You accept S1's forbid as permanent and related(a,b) as the only home for "same work" relations. Two strictness calls ride along, both #346's own post-ruling lines: priority NOT NULL and origin NOT NULL. Answer "B without the strictness" if you want the flatten only — they are separable.
The decision
A or B — one entity shape for the import stage.
Rec: B — flatten. (1) The ratified intent already chose it: S1's ruling and #294's plan both say the join goes; 50f4933 followed a schema section written before that consequence landed. (2) The flat schema is built and red-proved, not proposed — re-verified green on this lane today. (3) The window where flattening is free closes at the import stage; that is the entire urgency. (4) The split's only win (G5) is already covered by S1's forbid plus the related(a,b) table you asked for at 01:23.
What a ruling means, and what it does not
Ruling B authorises merging wt/294's ledger_store.py, test_ledger_store.py and the inc-1b plan note onto master as increment 1b, replacing increment 1's entity shape. Ruling A closes the fork and the import stage proceeds on 50f4933's schema. Either way, nothing else is authorised: no import, no cutover, no CLI, no rename — those stay gated on #263 lane H and #352.
