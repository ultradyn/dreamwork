One node, three products

pre-plan · no build authority
architecture review · 26 July 2026 · plans: dreamhub-platform.md, dreamnode-api.md

You asked for an architecture that is great to run locally or over a LAN/mesh VPN, and can become a website selling persistent tunnel access to your own machine, and can sell the hosted agentic experience. Those look like three products. They collapse into one stack if the architecture accepts a single claim: the paid tunnel and the hosted dreamer differ only in who owns the machine the node runs on, and the free local product is the same node with the relay switched off.

Recommendation. Put the seam at a small versioned node API — resources with ETags, an event stream of change notices, intents that return durable receipts — and make every surface a client of it: the local page, the hub, the website, the phone, the sandbox. Then take the first four stages regardless of whether the business happens, because every one of them fixes something that is wrong on your own LAN today.

What this proposes, in six lines
01One process per machine, not per project. dreamnode grows out of dreamhub.py: registry, the .dreamwork/ readers and writers, the runtime adapter, one API. Still stdlib, still no build step, still snapshot-deployable.
02Only the node knows what a .dreamwork/ is. The relay, the website and the hosted runner move opaque JSON. That is the existing hub rule promoted one level, and it is what makes a second repo safe.
03Resources and change notices replace the god snapshot. /data.json is 320,840 bytes on this repo, re-fetched on every change. A fleet row is hundreds.
04Writes become intents with idempotency keys and durable receipts — which is #274 and #263 landing once and serving both local duplicates and at-least-once relay delivery.
05Three auth planes, not one: node → relay (signed keypair, local unlink), browser → relay (own the account record), browser → node (bearer by QR, keeping #233's Host/Origin gates).
06The free local product must never require us. No account, no relay, no network — with a gate that proves it rather than a promise that says it.

The decision that is not technical

D0 · selling this makes people who are not you into users

Every goal in DREAMWORK.md is written about one human, deliberately, and dreamhub-design.md says so in as many words: one glance tells him which of his dreamers has stopped moving. A tunnel subscription and a hosted dreamer bring support, uptime, hostile peers, other people's source code, refunds, and a compatibility promise where today there is a migration note.

This is a goal change, not a surface change. The loop's own philosophy says scope expansion defers to you, so it needs ratifying in DREAMWORK.md rather than inferring from a request for an architecture. Rec: ratify it when the relay stage is authorized — and not before, so the early stages stay honest local improvements.

P2 is the good business — marginal cost in bytes, a small trust ask, and no abuse team. P3's margin is thin and volatile, because the dominant cost is somebody else's token bill. So: P2 first, P3 only after two numbers exist.
The architecture

The node dials out, and the relay never dials in — so there is no port forwarding, no DNS and no certificate for the user, and CGNAT works. The dashed path is a browser on the same LAN or mesh VPN talking to the node directly: the relay is not in it and never has to be. Review artifacts are served from their own sandboxed origin, because they are raw repository HTML.

dreamnode

Their machine. Registry, the only interpreter of .dreamwork/, the runtime adapter, and the /v1 API. Stdlib, no build step. Works with the relay unreachable.

relay

Ours. The node dials out over WSS, so no port forwarding, no DNS, no certificates, and CGNAT works. Authenticates, multiplexes, queues sealed intents, fans out push, optionally caches a summary. Stores no project content and parses nothing.

web app

A new shell — login, fleet, absent-node states, billing — around the extracted watch client. One project view, not two.

artifacts

Separate, sandboxed origin, because /reviewraw serves raw repo HTML and today it is same-origin with the dashboard.

hosted runner

A node that happens to be ours: sandbox, coding CLI, checkout, heartbeat, spend cap — speaking the same protocol a laptop speaks.

direct path

LAN or mesh VPN straight to the node with a bearer token. The relay is not in this path and never has to be.

The load-bearing choice · where the seam goes
1 · reverse-proxy the watch instances

Cheapest, and what daemon-mode.md originally sketched. Needs the URL prefix (#133) anyway.

Caps the product's UI at whatever a single-file Python renderer can express — no seam for a login shell, a fleet, billing, or an offline state. Keeps the 320 KB payload. N processes per user, N auth surfaces.

2 · a node API · recommended

One process per machine owning the registry, the readers and writers, the runtime adapter, and a versioned API. Every surface is a client.

Makes the central claim true: the website and the sandbox consume the API a laptop serves, so P2 and P3 stop being separate products to build.

Cost, stated: it needs #124's server-core seam and the client extraction. Taken in slices that each pay off locally first.

3 · rebuild watch and the loop as a service

Rejected for the reason daemon-mode.md already rejected it: it discards the session model and the harness tooling.

And it moves the file-format interpreters into a server we host — inverting the property that makes the free local product possible at all.

TLS terminates at the relay, so the relay can read live traffic — and end-to-end encryption against ourselves is theatre while we also serve the client JavaScript. What sealing genuinely buys is protection at rest: an answer typed on a phone while the laptop is asleep is a small write-only payload the relay never needs to read, so it should be sealed to the node's key and we should be unable to decrypt our own queue. The sending device can still show your words, because the browser already records every submission before the request leaves (#175). Another device says queued from your phone without the text. That is a real limit, stated rather than papered over.
Authority · what a remote session may do
An authenticated web session on a linked node is remote code execution on that machine. The loop steers an agent that runs commands, edits files and pushes to git. "Answer a question from the pub" and "run arbitrary code on my laptop from the pub" are the same feature from two angles, and the design and the marketing copy both have to say so.
ClassExamplesOver the relayOver a LAN token

Enforced at the node, never at the relay, so a relay compromise costs a short window rather than the fleet. The node keeps a local audit log of every intent it accepted and every one it refused — a file you can read without us — and revocation (tokens revoke, unlink) works while we are down or unpaid. The grant vocabulary is the one the ud-dreamwork-github plugin already uses: nothing is granted until it is named.

TLS on the LAN is the unsolved part — four honest answers

a · plaintext on a trusted LAN, exactly as #233 ships today, documented as such. Correct default, wrong for a coffee shop.

b · let the mesh VPN be the encryption — Tailscale or WireGuard, which is what you already have and the reason "meshvpn" is in the ask. The bearer token becomes defence in depth rather than the only wall. Rec: this is the documented path.

c · self-signed certificate pinned through the QR. Works, and every browser will still find a way to be unpleasant about it.

d · the service issues a real certificate for a name that resolves to a LAN address (the trick Plex uses): https:// with a valid certificate on a home network, zero configuration. This is plausibly the strongest reason a purely local user would ever pay us — a benefit that sends nothing anywhere.

Staging · the first four pay off with no business at all
Decide, and measure three numbers. No build. D0–D12 answered, then three spikes that each end in a number rather than an argument: what a fleet view and one project view really cost per hour on the new protocol; what one real dreamer costs in tokens and dollars over 24 hours; and whether a coding CLI can be driven headless in a container for a day — plus what its vendor's terms say about doing that for someone else. Catches a pricing page derived from a model, and a hosted tier that is legally impossible.
Resources, summary and ETags on watch.py, inside #124's server-core seam. dreamnode — registry, N-project reads, /v1, SSE notices, intents with receipts, per-project confinement, the bearer plane (#276). The hub page becomes its client; watch.py keeps working standalone. Client extraction and prefix-safe routing — #133 solved at the source rather than shimmed, all three root-absolute sites fixed. Gate: every existing browser guard passes against the extracted client, and a prefix-mounted deep link renders the right view — the exact silent failure origin-per-project was chosen to avoid. Catches the website and the local page becoming two project views.
The local product, finished. Bearer link by QR, PWA, local notifications, the mesh-VPN document, artifact origin isolation. Gate: a phone on a mesh VPN answers a question and the loop folds it. Catches a paid tier justified by withholding something that should be free.
Relay and website (new repo). Node link protocol, accounts, fleet across machines, live proxying, sealed offline queue, push, billing. Gate: a laptop lid closed mid-answer; the answer arrives when it opens; one receipt, not two; the relay cannot decrypt its own queue. Gate: a tenant cannot reach another tenant or the control plane; a spend cap stops a loop cleanly at a committed boundary. Catches an isolation story asserted rather than attacked.
The economics of a hosted dreamer have an unusual shape
The 4.75-minute heartbeat exists to keep the model's prompt cache warm, and provider caches expire in minutes. So a paused-and-resumed dreamer does not merely lose time — it loses the cache and pays full input on the next tick. Hibernation is a false economy for an active dreamer and only makes sense for a paused project. The cost floor per active hosted dreamer is therefore a small always-on machine plus continuous token spend, and the token half dominates by an order of magnitude.

Which is why the recommendation is BYOK at launch, bundled credits only once the per-dreamer distribution has been measured on three project shapes rather than modelled once. It is also why hosted is the second paid tier and not the first.

The decisions

Thirteen answers unblock the rest. D0 and D1 unblock everything.

D0
Is "users who are not Max" a stated goal?
Rec: yes, ratified in DREAMWORK.md when the relay stage is authorized — not now, so the first four stages stay honest local improvements.
D1
The seam: node API, proxy-over-watch, or rewrite?
Rec: the node API.
D2
May the platform repo be non-Python with a build step, while the node stays stdlib and build-free?
Rec: yes. The constraint exists to keep the thing that runs on your machine simple, not to bind a website.
D3
One project view, or two?
Rec: one — extract the watch client and mount it in the website shell. Two views diverge on the first fix applied to only one of them, and 120 KB of decided design does not want a second opinion.
D4
Authority defaults over the relay.
Rec: read, respond and steer allowed; lifecycle and runtime denied until granted per project; node configuration never remote.
D5
Does the relay cache summaries so the fleet works while a machine is asleep?
Rec: not in v1. Opt-in per project afterwards, with the page always saying how old a cached row is — a stale row that reads as live is the most expensive wrong impression this surface can give.
D6
Identity: own the account record behind a swappable broker, or adopt a full auth vendor?
Rec: own the record, keep a verified email, treat shoo.dev as an acceptable front door for the free tier.
D7
LAN encryption story.
Rec: mesh VPN as the documented path; plaintext trusted-LAN as the explicit fallback; service-issued LAN certificates filed as a paid-tier benefit.
D8
Tunnel: own the link protocol, or embed an existing reverse tunnel?
Rec: own it, kept small. A generic tunnel forwards bytes and knows nothing about accounts, intents or capabilities — and authorization is the product here, not transport.
D9
Hosted launch model: BYOK only, or bundled credits?
Rec: BYOK only until U2 is measured.
D10
Pricing shape.
Rec: tunnel tier per account with a node allowance; hosted tier per running dreamer plus their own model bill. No metered relay billing at launch — it punishes exactly the engaged users.
D11
Sequencing.
Rec: the first four stages regardless, because they fix present defects; then relay and website; then hosted only after U1 and U2 are closed.
D12
Does any of this touch watch.py outside #124's planned seam order?
Rec: no. Two of these stages are those seams, and should be dispatched as #124 work with this plan as their motivation — not as a parallel track that re-splits the same file.
What approving this artifact would mean: the architecture direction is accepted and the numbered decisions are settled. It would not authorize a build — not even the measurement spikes. Those are separate asks, one stage at a time, in the plan's order.
