You asked whether a task transition should share #263's journal or use a task-state outbox, "but never dual-write two fallible truths". The answer is neither, and for one reason: both options assume a task transition and a user event are the same kind of fact. They are not. Your constraint forbids storing one fact twice — it does not forbid storing two facts and joining them with a foreign key. Full design at .dreamwork/docs/plans/task-transition-boundary.md.

Recommendation. Task history is its own append-only task_event log, in the same SQLite file as #263's journal, appended in the same transaction as the compare-and-swap that moves task state. No outbox, no drain. Burndown and the dashboard status section become queries over that log — not tables, not caches, not files — so neither can be stale. One materialised row survives, and only because a claim needs something to CAS against.

The shape, and the rule that keeps it small
BEGIN IMMEDIATE;                    -- not deferred: deferred takes the write lock late
  INSERT INTO task_event(...);      -- ordinal, cause, actor, receipt_id?, prev_hash, hash
  UPDATE task_state SET ..., revision = revision + 1, at_ordinal = <new ordinal>
    WHERE task_id = ? AND revision = ? AND <the verb's own predicate>;
COMMIT;

Outside it, always, and never load-bearing: the tasks.md export, the watch-events.log wake line, and any file an agent writes by hand.

the governing rulea materialised row exists only where a writer must compare-and-swap against it. Everything a reader wants is a query. Exactly one table qualifies
task_eventauthoritative, append-only, never updated, never deleted — including by purge, because burndown needs 2026's landings in 2027. It carries no submitted bytes precisely so no retention policy ever needs to reach it
task_statethe one materialised row, and only because grab needs something to CAS. Rebuildable, and verified by replay
at_ordinalthe load-bearing column: it names the event that produced the row, so "is this current?" is a comparison rather than a belief — and a hand-edited row becomes detectable, which a bare state column is not
burndowna GROUP BY. Today it is 331 git shows memoised on HEAD because it is expensive; over a few thousand rows it needs no cache, so there is no cache to go stale
blockedderived from the dependency graph plus a small gate table for "blocked on you". Never written, so it can never drift — and landing #263 makes every dependent selectable with zero writes. Today that is free prose in 28 entries and hand-annotated UNBLOCKED in 4
status.jsonkeeps what is genuinely a live process's own claim — the prose, the goal, the agents, the monitors. Loses queue, current_task_ids and per-agent task_ids. That is the direct reading of your "no agent hand-editing status.json"

One database file, and this one is measured rather than argued: SQLite has no syntax for a foreign key into an ATTACHed database (near ".": syntax error, 3.53.3). So the task_event.receipt_id → receipt check can only exist inside one file. Two files reduce it to an unvalidated string — the exact "single truth across two stores" hazard.

Two footguns, made into checked invariants
footgunwhat silently breaksthe check
PRAGMA foreign_keys is OFF by default, per connectionevery reference — receipt_id, task_id, the enum lookups — validates nothing on any connection that forgotset in one place; a test asserts a violating insert raises
plain BEGIN takes the write lock latea read-then-CAS transaction hits SQLITE_BUSY mid-transaction, where retrying is not safe. Under concurrency this is the common failure, not the rare oneBEGIN IMMEDIATE everywhere; a two-process test proves one writer wins and the other retries cleanly

And one difference from #263 worth stating: an expired receipt claim may be quietly reclaimed, but an abandoned task claim appends a lease_expired event naming the prior owner. Which dreamer vanished, and when, is what the file-ownership invariant reads — a silent reclaim would delete the only durable trace of a dreamer that died mid-increment.

What to decide
T1 · The boundary. Task history is its own append-only task_event log in the same SQLite file as #263's journal, appended in the same transaction as the state CAS; burndown and the status section are queries; the receipt link is a foreign key, not a shared transaction.
Rec: take it. It is the only one of the three shapes where each fact has exactly one home, and it is the smallest — one materialised row in the whole design.
T2 · status.json loses its task-derived fields — queue, current_task_ids, per-agent task_ids — and the dashboard queries the store instead.
Rec: yes. Those three fields are the measured 122-vs-113 disagreement. Everything else in the file is a live process describing itself, which is what status.json is for and stays.
T3 · Does the burndown have to survive a fresh clone? Today it does, because git history is the source and the ledger is committed. A SQLite store is gitignored and machine-local, so a clone would start with no history.
Rec: yes, and it costs nothing now. Defining the log's canonical byte form on day one (the hash chain needs one anyway) makes a committed append-only text export a provable projection — so this becomes a deployment choice later instead of a schema change. Say if machine-local is fine and it gets simpler; this is the one answer that could still move the shape.
T4 · Does anything else read the burndown or the status section that this would break?
Rec: only you know. #334 is live on burndown.mjs and #281 on /tasks; both were reasoned about, neither was touched. If there is a consumer outside the dashboard, it changes the export question.
What approval means, and what it does not
Approving accepts the boundary and nothing more. It does not authorise creating a table, writing a CLI, migrating, cutover, deleting anything from status.json, touching tasks.md, PostgreSQL, or payload purge — those wait on #263's implementation gate exactly as the rest of #294 does, and this document inherits every limit that gate states. Thirteen red-first fixtures are drafted, each naming the production line that must change for it to fail, and two of them naming the fixture-shaped way the check could pass hollow.
