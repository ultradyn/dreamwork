The four options, on the three axes that decide it

His redirect (“self-hosted with a tunnel or over a shared mesh or lan — we should aim for simpler auth methods; ssh tunnel, session key auth’d via ssh (magic-link esq), user/pw, sqrl if possible”) names four options in cost order. Each is answered in full in the plan (.dreamwork/docs/plans/hub-ssh-auth.md) against six bullets; this table is the decision view — the trust root, the per-device operator cost, and the “lost my phone” revocation story, which is the question that separates a design from a wish.

optiontrust root & what an attacker without it cannot do operator cost (per new device)revocation (lost phone)
1. ssh tunnel document now the device’s ssh private key. Attacker without it cannot reach the hub at all — the hub is invisible off-host and holds no credential. zero implementation. ~10–15 min on a phone (ssh app + key + forward); one ssh -L on a laptop. remove the key from authorized_keys; live session dies on its keepalive. permitopen scopes a key to the hub port only.
2. session key over ssh build first ssh (to run the issue-command) + a one-shot token traded for a cookie. Attacker without ssh cannot mint; an on-LAN eavesdropper without the token gets 401. Token is one-shot — a logged token is dead after first use. moderate build (~3 incs: issue/store, middleware/cookie, redacted /summary.json). Per device: one ssh … issue-session + a scan/paste — no key management on the device, which is the point. dreamhub revoke-session --all (or --note phone); phone 401s on its next request. Sliding cookie TTL + token dies in ~5 min if unused.
3. user / password fallback a shared, reusable secret. Attacker without it cannot log in — but it can be phished, replayed, guessed, reused. The TLS gap is the real cost: over HTTP on a LAN the password is sniffable, so this needs the tunnel (redundant) or a Caddy (his Q2). moderate-to-high and mostly redundant. scrypt ~105ms/verify (stdlib) is fine; login form + session store shared with option 2; rate-limit mandatory (~9 verifies/sec). Cheapest per device (type a password) and the weakest. change the password (one global password ⇒ revokes everyone). Per-user accounts add complexity for little gain on a single-operator hub.
4. SQRL no a per-site derived key from a master key. Cryptographically interesting; ecosystem not. Ed25519 verify is not in Python’s stdlib — the same wall that blocked shoo’s ES256 in #275. not worth measuring. Dormant ecosystem (sqrlid.com defunct, thin clients), idiosyncratic protocol, third-party crypto. Even a survey impl is not worth the dependency. moot — do not build. Honest “no”: not broken, but not alive enough to bet an agent control plane on.

Full per-option detail (six bullets each, plus the ssh-tunnel recipe and the failure modes) in .dreamwork/docs/plans/hub-ssh-auth.md. scrypt figure measured this session on this host with stdlib hashlib.scrypt; all other claims are grounded in dreamhub.py, hub-public-auth.md, lan-bind.md, and the OpenSSH man pages.

Relationship to hub-public-auth (#275) and #276

This plan supersedes the identity recommendation of hub-public-auth.md and extends its boundary shape; it does not duplicate it. The threat model, asset inventory, TLS/proxy analysis and the /data.json-leak finding (C2) are #275’s and are inherited, not re-derived. What is superseded is the identity layer — Cloudflare Access / Tailscale Funnel as the authenticating boundary — replaced by ssh as the trust root, with a local Caddy (his Q2 ruling) carrying TLS so the control plane stays on the operator’s host. #276 (LAN bearer token) is superseded by option 2 if the ssh-issued session lands: same transport, but short-lived, revocable per-device, and not a static string the operator guards by hand. If option 2 does not land, #276 stands.
