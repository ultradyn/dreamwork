Goal hierarchies

design review · task #95 · plan at .dreamwork/docs/plans/goal-hierarchies.md

You asked for goals, hierarchies of goals, a session goal and a task goal — and, for your own goals, a hierarchy with a known current branch. This is what that would mean mechanically, and the three decisions it needs from you.

The idea

Alignment is currently a judgement call: the scope gate asks whether a piece of work "fits DREAMWORK.md". That works while the loop is small and you are watching. It degrades exactly where it matters — long sessions, delegated dreamers, work you did not see start.

Making the chain explicit turns that judgement into something checkable: every piece of work names the path from your highest goals down to the increment in hand. The scope gate stops being "does this feel aligned" and becomes name the chain — and if you can't, it parks in questions.md rather than getting built.

One tree, four depths

That chain is not invented for the diagram — it is this morning, read bottom-up from the work you watched land. #97 existed because the restart proved the queue was not durable; that served a sub-goal about the loop's memory; which serves the goal you actually care about, which is being able to walk away.

"User goals" and "task goals" are depths, not kinds. One tree: your goals at the root (DREAMWORK.md, nested, human-edited), durable sub-goals accreting underneath as work reveals them, the session goal declared at init and living in status.json, and the task goal as two fields on the task itself.

What it deliberately is not
  • Not a planning bureaucracy. Chains are one-liners named at task start — never a document per goal.
  • Not a new file. The tree lives in files that already exist: DREAMWORK.md, status.json, task metadata.
  • Not retroactive. Existing tasks are not back-filled; chains attach as work is started.
Three decisions

1. Where do session goals persist?

status.json is ephemera — gitignored, rewritten every tick. A session goal written only there dies with the session, which is precisely the failure that cost eight tasks this morning.

Rec — they don't persist
A session goal that outlives its session was a durable sub-goal all along; wrap-up promotes it into DREAMWORK.md. Keeps the tree honest and the file short.
Alternative — a session log
Append each session's goal to a durable list. More history, but it accretes noise: most session goals are not worth keeping, and the ones that are belong in the tree anyway.

2. Should selection enforce branch focus, or just state the chain?

Enforcing means the selection algorithm prefers tasks on the active branch of the tree, so the loop finishes a line of work before wandering.

Rec — state only, first
Naming the chain at task start makes drift visible. Add preference weights only if drift actually shows up. Cheaper to add later than to unpick.
Alternative — enforce now
Stronger focus, but it fights the loop's character: the free-flowing "potter productively" quality comes partly from being allowed to pick up the adjacent thing.

3. Task parent: free text or stable ids?

Rec — free text matching DREAMWORK.md headings
Human-readable in the file and on the dashboard; the coherence rotation catches dangling names, which is a real check that already runs.
Alternative — stable ids
Rename-safe, but adds an id space to a file you edit by hand, and makes the tree less readable in exchange for a rename that is rare.
What lands, if you say go
  • SKILL.md: task conventions gain goal/parent; selection states the chain; the scope gate becomes "name the chain". DREAMWORK.md template and this repo's own file gain nested Goals.
  • Init and wrap: session-goal declaration, and wrap-time promotion of any session goal that turned out to be durable.
  • status.json gains goal; the dashboard renders the active chain (a dreamer's job — it touches watch.py).
  • A migration entry for the task-metadata and status.json shape.

One open risk worth naming: this is the loop adding ceremony to its own work, and ceremony is what the philosophy warns against. The mitigation is that a chain is one line stated aloud at task start, not a document — if it ever costs more than that, it has failed and should be cut.
