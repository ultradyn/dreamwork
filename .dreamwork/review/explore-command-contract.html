Explore before committing

proposal · task #225 · command contract, not implementation authority

Recommendation: add a hidden command named explore. It asks the loop to investigate whether and how an idea should proceed, then returns one concise, self-contained HTML decision artifact. It may recommend later tasks; it never starts implementation itself.

Why now: the threaded-chat request just became the first manual example of this work, and produced exactly the desired decision artifact through an ad-hoc command. Naming the repeatable contract now prevents the next exploration from depending on remembered prompting.

Why this name
explore · survives

Does not presuppose one solution, covers feasibility and alternatives, and reads naturally beside “add idea” and “do now”.

create proposal · refuted

Promises a proposal before the investigation has established that anything should be proposed.

feasibility check · refuted

Too narrow: an idea may be feasible yet wrong for this project, or need comparison among several viable shapes.

Exact contract
input
A question, feature idea, architecture possibility, process change, or “how might this work?” prompt. The human need not pre-structure it.
mode
Hidden/non-default composer kind. Submission creates a normal human-originated task and dispatches a fresh research/design subagent when capacity permits; the main loop remains free.
output
One offline-clean HTML artifact under .dreamwork/review/, linked from one questions.md approval entry. Concise recommendation first; diagrams/comparisons only where they clarify; deeper evidence in disclosures.
decision method
State context and binary goals; compare real alternatives decisively; recommend the one non-refuted option, or say what unknown prevents a recommendation. No scores or decorative pros/cons.
authority
Proposal only. The exploration may name tasks but cannot implement, deploy, change policy, or enqueue its own recommendation as active work before human acceptance.
failure
Human words are witnessed before dispatch. A failed/aborted worker leaves the task open with a named failure and no fake artifact. Resume or re-dispatch uses the same durable prompt/task.
Lifecycle

04 · presentWrite and visually review the concise artifact.
05 · decideHuman approves, changes, or defers. Only approval creates follow-up work.
Artifact acceptance
  • Recommendation and “why now” are understandable without opening any disclosure.
  • At least two genuine alternatives are shown when alternatives exist; the recommendation is not a foregone conclusion.
  • Unknowns, risks, and the smallest useful experiment are explicit.
  • Desktop and mobile renders are inspected; geometry and visual reviews pass the same revision.
  • Every proposed action is marked approved now, deferred, or requires human approval.
  • The final approval prompt can be answered in one short line.
Relationship to #229 topic chats and #230 use-subagent

explore is a one-shot decision product: one prompt, one fresh investigation, one reviewed artifact, one approval boundary. #229 topic chats are repeated turns around a durable subject; #230 asks for a general composer switch that may parallelise arbitrary commands. They may later share worker-lifecycle machinery, but neither is required to ship the command contract.
