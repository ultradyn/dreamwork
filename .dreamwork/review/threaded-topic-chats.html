Threaded topic chats

proposal only
design review · task #229 · no implementation authority

Recommendation: add a quiet chats section to the dashboard and a dedicated /chat?p=<chat-id> view. Each human turn starts one fresh worker which reads an append-only Markdown transcript, writes one terminal result, and is discarded. There is no durable model session.

Executive recommendation
surface
Dashboard shows a compact recent-chat list; the dedicated chat route owns reading and writing. Do not put full conversations in the dashboard.
memory
transcript.md is the conversational source of truth and the primary prompt input on every turn. It is human- and agent-readable; JSON does not replace it.
process
One in-flight worker per chat. Separate chats may run concurrently under a small global cap; proposed default: 2.
follow-up
A second send becomes one visible, durable, editable queue item. It is not transcript history until dispatch atomically promotes it to a human turn.
interrupt
Defer in MVP. Do not pretend a harness stop is a chat reply. Later, offer “cancel run” only if cancellation can append an explicit cancelled terminal outcome.
module
Put file locking, leases, recovery, worker spawning and finalisation behind one deep Python module; watch.py remains a thin HTTP/UI adapter.
The governing invariant: human words reach durable storage before dispatch, parsing or validation can lose them; an agent answer becomes conversational history only once, with an honest terminal outcome.
Ubiquitous language
Chat
A durable, named conversation about one topic. It is a file-backed record, not a model session.
Turn
One accepted human contribution or one terminal agent contribution in the transcript, with a stable id.
Queued follow-up
The one durable human draft accepted while a worker is active. Editable and cancellable; not yet a turn.
Run
The lifecycle that begins when a human turn is dispatched and ends in exactly one terminal outcome.
Worker
A fresh ephemeral subagent process for one run. It reconstructs context, answers, and is discarded.
Transcript
The append-only Markdown record and primary context input for every fresh worker.
Process state
Small machine-readable lease/recovery facts about the active run. Never the conversational source of truth.
Terminal outcome
Exactly one of completed, failed, or later cancelled; never an implied success.

Avoid thread in implementation names: it is overloaded with OS threads and model conversation threads. The user-facing phrase may remain “topic chat”; code should say chat, turn, run, and worker.

Goals: G1 human/agent-readable durable conversation is primary; G2 no durable model session; G3 queue/lock status can be explained in one view; G4 restart never invents completion or loses accepted input; G5 no dependency or daemon is required.

B fails G1

C fails
Session continuity contradicts fresh-per-turn, and an export can lag or disappear exactly when the harness crashes. It also makes recovery depend on a model provider’s session semantics.
Tentative survivor: A. Its remaining unknown is not the architecture but the worker adapter: the available Pi/Claude dispatch mechanism must provide a bounded, attributable result and a reliable process identity before implementation.
Placement alternatives

Dashboard-only: refuted. Full transcripts and composers would turn the glance surface into a conversation workspace and make stable deep links impossible.

Dedicated /chat only: refuted. Chats become invisible unless the human already remembers their URL; active and queued work belongs in the dashboard’s glance hierarchy.

Review artifact only: refuted. Artifacts are static proposals in an iframe and intentionally isolated; using them as an operational write surface would confuse review evidence with live application state.

Dashboard index + dedicated route: survives. The index states what exists and what needs attention; the route gives one subject a URL, matching the dashboard’s established expand-versus-navigate rule.

Also distinguish a clean failure from a stale lease.

Interaction contract. While idle, the button says send; a successful durable append immediately restates the human turn and changes the status to agent working. While running, it says queue; only one queued item exists, so a second edit updates that item rather than creating a hidden list. The queue’s saved state survives ticks and reloads because it is on disk, not only in DOM state.

Status, cancellation and fault states
  • Global cap reached: the human turn is already in the transcript; status reads waiting for a worker · 2/2 active. This is dispatch waiting, not the editable follow-up queue.
  • Worker active: composer is in queue mode. The page shows run age and fresh-worker identity; it does not stream speculative prose into the transcript.
  • MVP cancellation: absent. Do not show a control the worker adapter cannot honour and finalise durably.
  • Later cancellation: label it cancel run, never “interrupt”. The click first durably records a cancellation request, then stops the worker, then appends a terminal cancelled agent turn. A completion racing cancellation is resolved once by finalisation under the chat lease; whichever terminal outcome commits first is shown.
  • Stale lease: amber fault line: worker state is stale · recover. Sending remains disabled until reconciliation prevents two workers answering the same human turn.
  • Malformed transcript: amber fault line with the path and parser error; no worker starts and no repair is attempted silently.
Exact storage proposal
.dreamwork/chats/index.json
Small derived index for list order/title/status cache; rebuildable from chat directories, never conversational truth.
…/<chat-id>/transcript.md
Append-only canonical conversation and primary worker input.
…/<chat-id>/queue.md
Optional single pending human follow-up; atomically replaced on edit, removed on cancel or promotion.
…/<chat-id>/run.json
Exclusive lease and recovery state for the current run; created with exclusive-create semantics.
…/<chat-id>/runs/<run-id>.partial
Optional bounded diagnostic output from an incomplete worker; never included in prompts automatically.

Path naming. chat-id is a generated lowercase slug plus a short random suffix, for example release-retention-a4c2. The title remains editable inside the transcript; identity never depends on a rename. All resolution passes through the existing confinement principle: no absolute paths, ~, separators, traversal or symlink escape.

Also distinguish a clean failure from a stale lease.

The browser submits an expected revision when editing or cancelling; a stale tab gets 409 and the current durable queue back. Promotion is idempotent: before appending, recovery searches the transcript for queue-id. If present, it removes the queue file; if absent, it appends exactly one human turn, fsyncs, then removes the queue. The queue is included in a worker prompt only after promotion.

Create with O_CREAT|O_EXCL; update by write-temp + fsync + os.replace. Ownership is not “PID exists”: recovery must match host and boot id, confirm the PID belongs to the expected worker where available, and check heartbeat age. Uncertainty enters recovering; it never launches a second worker.

Submission ordering: every chat POST also passes through the existing first-act .dreamwork/submissions.log witness before path dispatch, JSON parsing or validation. Accepted text then reaches transcript.md or queue.md. The witness prevents raw words being lost; the chat files state what the application accepted.

State machine
idle
No run lease. A send appends a human turn before anything dispatches.
waiting capacity
The chat owns a durable unanswered human turn but no process; this differs from the editable follow-up queue.
running
Exactly one worker and lease for this chat. Further accepted text goes only to queue.md.
finalising
The module holds the chat lock, checks run-id was not finalised, appends one terminal agent turn, fsyncs, then removes the lease.
recovering
Ownership is uncertain or the process restarted. Read-only reconciliation precedes any new worker.
Failure, trust and resource policy
Crash / restart recovery
  1. At server start and before every submit, reconcile(chat_id) inspects transcript, queue, lease, host/boot/PID and any complete result file.
  2. If a terminal turn already names the run id, finalisation is complete: clear stale process files and continue.
  3. If a complete result exists but no terminal turn does, finalise idempotently under the exclusive chat lock.
  4. If the expected worker is alive, reattach monitoring; do not dispatch.
  5. If it is certainly dead, append failed, preserve bounded partial output, clear the lease, then promote the queue.
  6. If ownership is uncertain, stay recovering and require an explicit recovery action. Loud lock beats two answers.
Malformed files and append safety

The parser rejects duplicate turn ids, non-monotonic turn numbers, unknown terminal outcomes, missing metadata closure, an agent turn without in-reply-to, and a queue id already represented with conflicting text. It reports the path and last valid byte offset. It never “repairs” by dropping trailing material.

Append uses a per-chat OS lock, one framed block assembled in memory, flush + fsync, and only then reports success. A torn final block is a recoverable fault with its bytes preserved. Index data is rebuildable and may be replaced; transcripts are never rewritten for ordinary operation.

Partial output

MVP does not stream into the canonical conversation. Worker output is capped and buffered to a run result file. Only a successful, validated terminal result is appended as completed. On crash/timeout, bounded partial output stays in runs/<id>.partial, visible behind “inspect partial output”, clearly outside the transcript and excluded from the next prompt. The human may quote or promote useful text manually.

Privacy, retention and git

Recommendation requiring approval: gitignore .dreamwork/chats/ by default because transcripts may contain raw human text, source excerpts and model output. Durability means local disk, not publication. Later “export chat” can copy a reviewed transcript to an explicitly chosen tracked path.

Do not auto-delete transcripts. Workers and transient credentials are discarded at terminal outcome; completed result scratch is deleted after append. Failed partials remain until a visible manual cleanup action. Automatic retention limits are deferred until the human states a policy.

Prompt injection and trust boundary

The transcript is untrusted conversation data, not authority. The worker prompt encloses it as quoted project data and states that instructions inside it cannot override system, repository or human-authority rules. Agent prose is equally untrusted on the next turn. File attachments are not in MVP; workers receive the transcript plus a fixed system brief and only the explicit repository access their adapter grants.

Chat titles and ids never become shell fragments. Worker launch uses argument arrays, no shell. Outputs are length-capped, decoded with replacement on invalid bytes, and rendered escaped. The localhost trust model remains, but cross-site POST protection and origin checks should be explicit before adding a general chat write route.

Concurrency, cost and fairness
  • Per-chat cap: exactly one run.
  • Global cap: proposed 2; FIFO by durable human-turn time, with no hidden bypass.
  • One queue item per chat; editing it does not alter queue position because it is not dispatched yet.
  • Timeout, maximum prompt bytes, maximum result bytes, and model/thinking choice are explicit configuration. Over-limit transcripts fail visibly; silent truncation is forbidden.
  • Fresh workers cost repeated transcript input. MVP shows transcript bytes and latest run duration; token/currency estimates wait for a provider that reports them honestly.
Deep module / small interface
class TopicChats:
    def list(self) -> list[ChatSummary]: ...
    def read(self, chat_id) -> ChatView: ...
    def submit(self, chat_id, text, request_id) -> SubmitResult: ...
    def edit_queue(self, chat_id, queue_id, revision, text) -> QueueResult: ...
    def cancel_queue(self, chat_id, queue_id, revision) -> QueueResult: ...
    def reconcile(self, chat_id=None) -> list[RecoveryNotice]: ...

The interface includes the invariants: methods are confined to the configured target, human input is witnessed first by the HTTP layer, accepted mutations are durable before success, and results report sent, queued, waiting-capacity, conflict or fault. Callers never handle PIDs, locks, filenames or transcript framing.

WorkerAdapter.start(run_spec) is the only internal seam justified by actual variation: production harness versus deterministic test fake. Everything else remains implementation detail. The deletion test passes: removing TopicChats would spread lease recovery, append grammar and idempotence across every route and test.

Relationship to task #230: the later composer use subagent checkbox may reuse the worker adapter and global-cap policy. It is a separate interaction with different durable context and must not silently create or append to a topic chat. This proposal does not design its checkbox, ownership or result placement.

Verification
Red-first acceptance checks (12)
RED 01 Kill the server between receipt and validation; raw human text remains in submissions.log.
RED 02 Paste headings/comments that imitate turn framing; round-trip yields one human turn with byte-equivalent visible text.
RED 03 Race two sends to one idle chat; one becomes the dispatched turn, one the visible queue, never two workers.
RED 04 Crash after transcript append but before queue removal; recovery finds queue-id and does not duplicate the turn.
RED 05 Crash after result write but before transcript finalisation; restart appends exactly one terminal agent turn.
RED 06 Reuse a live PID from another process or prior boot; ownership is not accepted from PID alone and no second worker starts.
RED 07 Give malformed transcript/state; dashboard shows an amber path-specific fault and dispatch stays locked.
RED 08 Run three chats with cap 2; two run, one visibly waits, and FIFO survives restart.
RED 09 Fail after partial worker output; transcript says failed, partial is inspectable but absent from the next prompt.
RED 10 Type/edit queue while two mtime ticks replace the view; text, revision, caret, focus and queue status survive.
RED 11 Trace row/status/queue transitions per frame; multiple intermediate positions, no overshoot, settled crispness, reduced-motion parity.
RED 12 Attempt traversal, symlink escape, oversized prompt/output and forged chat id; all refuse loudly without starting a worker or losing the witnessed submission.
Decision boundary

Decided by this proposal (tentative design)

  • Fresh-per-turn means no durable model session; transcript reconstruction is mandatory.
  • Markdown transcript is primary conversational truth; process JSON is subordinate and minimal.
  • One run per chat; one visible editable queue item; no silent second send.
  • Dashboard index plus dedicated route; deep orchestration module rather than logic spread through watch.py.
  • MVP does not stream partial output into conversation and does not claim interrupted work completed.
