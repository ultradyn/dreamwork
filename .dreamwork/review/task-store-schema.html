Why this half can start without your #263 answer

#294's own entry said starting would mean designing "against an unsettled event model". Read against the document rather than from memory, that is not the state. user-event-journal.md:4 says "human approval required; no implementation authority", and its approval gate authorises "a separate red-first implementation plan". What #264 gates is one question: does a task transition share #263's journal or use a task-state outbox? That is about how a transition becomes durable. The shape that survives all five

Entry and identity separate — finding 1's only honest answer. Per-entry attributes live on the entry; task is permanent identity pointing at it, so #138 and #156 share one body that cannot disagree with itself.

entry(entry_id PK, state open|landed, title, body verbatim,
      priority band(P0-P3), priority_uncertain flag, type NULL, origin NULL, source_line)
task (id PK, entry_id -> entry, ordinal)
priority + priority_uncertaina closed band column (P0–P3) plus a flag for “could be higher”, so P0/P1 is band P1 with the flag set — orderable, groupable, no compound value
type NULLpopulated only from unambiguous forms; the migration reports what it could not read. #339's ruling: a misdetected value is worse than none
originthree values, and NULL only for entries whose greatest leading id is below 216 — an asserted invariant, not preserved looseness
dependency edgesnot parsed from prose. Today's blocked-on is free text; each stored edge keeps the exact substring it was read from, and every unparsed phrase is listed for you rather than guessed into a graph
review_decisionartifact as PRIMARY KEY is the "exactly one owning question" rule, so a conflicting second claim is refused at write time. unlinked is deliberately not a value — it is the absence of a row

Read verbs only: tasks list (open-only carries the landed count), tasks get <id>, tasks count, reviews list|get. No write verb exists under this id in any form, including a dry-run one.

Either the store's reader becomes the single implementation all three call, or that is accepted explicitly.

The four decisions

All four were the same question — how much of today's looseness is a feature to preserve? — and your 01:13 note inverts the answer. Because the plaintext is transitional, the sole objection behind S1, S2 and S4 was "that edits your existing entries": a one-time cost, weighed against looseness the schema would carry forever and every consumer would handle forever. So the recs below are revised to normalise the Markdown first, then let the schema be strict. S3 is withdrawn outright, for a different reason: finding 4 was wrong.

The one real cost, because it is not nothing. Normalising means bulk edits to the loop's own durable memory, and a fold script damaged questions.md earlier tonight by dropping a newline after a heading. So it gets its own task and its own guards — parse with the real reader before and after, assert the counts move only where a split is intended, diff every body for unintended edits — and it does not start without your ruling, because the entries are your words. It needs no #263 answer, so with #352 it is the second thing that turns "sqlite is a blocker" into movement.
S1 · Combined entries. Split #138/#156, #250/#251, #292/#293 into single-id entries before migrating and forbid new ones? Or keep them behind an entry/task split?
Rec REVISED to split on your note. The original rec was keep, and its only argument was that splitting edits three of your entries — spent, if the plaintext is on its way out. Splitting removes a table and a join permanently.
S2 · Compound bands. Resolve the four (P0/P1×3, P1/P2×1) so priority is a closed enum, or keep them legal?
Ruled: priority closes, and the bands stay. The three P0/P1 each still mean something (“at least P1, possibly the very top, not yet certain which”), so they stay — but the schema needs no compound value: a closed band column plus priority_uncertain holds “could be higher”. The P1/P2 was never ambiguity — it was #250’s P1 and #251’s P2 concatenated, and the split resolved it.
S3 · Origin. Withdrawn — nothing to decide. It rested on finding 4, which was wrong.
There are 50 unmarked entries, not 60; every one has an id below 216; so absence is your contract's forward-only cutoff, derivable from the id, and not a distinction anything needs to preserve. The schema asserts the invariant instead.
S4 · Is type a closed set? Close it at cutover (the ~10 real values), classifying the unreadable ones by hand first? Or free text with NULL?
Rec REVISED to close it. The refutation was that the migration cannot classify 172 entries correctly — and it does not have to, if they are normalised by hand first, with anything genuinely ambiguous left explicitly NULL rather than guessed.
