Input parity — the half nobody looks at
01Rows are links. Tab, Enter, middle-click and new-tab work with no JS; modified clicks already fall through isInternal. The facets sit inside the link, so the accessible name is the whole row and the whole row is one ~40px tap target at phone width.
02The count line is aria-live="polite". A sighted reader watches rows travel; a screen-reader user hears “38 of 104 open”. Without it, filtering is a silent event — the same class of failure as a fold that hides something in flight.
03Focus moves only on his navigation. To the detail title on open, back to the row on Back, and never on a tick — which is #179, the bug where his caret came back in the right place and dead.
04Blocked-on ids are plain text on the row and links on the detail. Nested links inside <a> are invalid; the accepted cost of making the row one honest target.
05/ focuses search and is ignored inside text fields — the rule the shader hotkey already obeys. Escape clears. No modal keymap is invented.
06Nothing load-bearing is hover-only. Hover is the weakest of the page's three detail idioms — invisible to touch and to a keyboard — so this page uses it for none of them.

Decisions wanted — one line each

Everything the recorded contracts already answer is decided above and its reasoning is stated. These seven are taste-or-authority calls that are yours; each carries a recommendation, so rec is a complete answer to any of them.

Q1
May /tasks claim a wider column on a wide screen — a two-pane list-plus-detail triage layout?
Rec: no, for v1. watch-design.md names /review as the deliberate width exception, and a second exception is how a one-column page becomes a two-column one. The morph plus a canonical URL gives most of the benefit, and a split view can be added later without touching the data contract.
Q2
Default sort: priority band first, or newest id first (the file's own order)?
Rec: priority, then newest id. Same reason questions.md sorts in the parse — the page's job is telling you what to look at first. The ledger is written newest-first, which is arrival order, not urgency.
Q3
Default filter: open only, or everything?
Rec: open only, with 17 landed in the count line and one click away. The page is for steering; 17 settled rows diluting 104 live ones is the opposite of ranking.
Q4
Is /tasks?t=281 the URL #282 should hardcode, or do you want /tasks/281?
Rec: ?t=281. It keeps the server's route allowlist an exact membership test, matches /file?p= and /review?p=, and needs no router change. /tasks/281 reads nicer and costs prefix routing in the same seam #133 will touch.
Q5
Should the loop's status.json claim (“I am on #281 right now”) be shown at all, given it is a claim and not a fact?
Rec: yes, labelled as the loop's claim, carrying this page's only accent. It is the sole in-flight signal that exists, and #294 is what turns it into a fact. The alternative is a page that cannot tell you what is happening now.
Q6
Do you want a write affordance on a row later — do now: #281 sent straight from the list?
Rec: not in v1, yes as a follow-up. It needs no new endpoint or vocabulary (/command and do-now both exist), so it is cheap — but it turns a read-only page into a steering surface, and that is a decision to make deliberately rather than fold into a list page.
Q7
File the three findings above as tasks?
Rec: yes. The combined-entry blindness is a P2 bug rather than a polish item — the burndown is on the dashboard and is under-counting right now.

Why the records ride their own endpoint rather than /data.json

/data.json measures 374KB today and is re-fetched on every open window every two seconds. The parsed ledger adds 139KB — measured, not estimated — for the benefit of one route.

files            145,851 bytes   (DREAMWORK.md + questions.md + lessons.md)
dreams_archive   100,996
answered_entries  42,660
questions_open    32,269
burndown           1,074   ← aggregate only, which is why it belongs there
—
tasks.md itself  103,391 bytes of Markdown

/filedata is the standing precedent for a route-scoped fetch. The client caches /tasksdata and invalidates on a changed /mtime, so liveness is unchanged and the cost is paid only where it buys something. #282's hovercards fetch one record — which is why the single-record shape exists at all.

And the client-side scan has a named ceiling rather than a discovered one: at ~600 entries or a list body over ~512KB, search moves behind #294's query API. A pytest asserts the current size, so the ceiling arrives as a red light instead of as a slow page.
