Multi-dreamer architecture

decision review · #96 lineage · 2026-07-26 · plan at .dreamwork/docs/plans/multi-dreamer.md

He asked for a plan for a multi-dreamer architecture and named the IGC method. This artifact is the decision surface: the goals, the options, and where each option is refuted. Nothing here is authorized to build. The ask at the end requests stage A only.

The goal it serves was recorded on 2026-07-25 in DREAMWORK.md: one human, several dreaming agents — the workflow scales past one session, a hub aggregates them, and managing an agent's lifecycle (spawning, steering, compacting, retiring) becomes something the system does deliberately rather than something the human improvises per client.

How to read the matrices

An IGC triple is idea × goal × context: an idea is never good or bad on its own, only against a stated goal inside a stated context. Goals run across the top, ideas down the left, and the All column is the whole point.

✔ satisfies the goal ✘ refuted — fix the idea or drop the goal ? unknown — an experiment, not a maybe

Ideas are not scored and not weighed. One ✘ refutes a row however many ✔s sit beside it, and a row holding a ? cannot be adopted until the ? is resolved. Repairing a refuted idea is a legal move, and it gets its own row rather than an edited cell — otherwise the record shows a plan that was always right.

Context — every mark below is a claim about this and nothing wider
  • One human. Agents are harness-hosted sessions: nothing in this repo can create an agent process, so spawn means the harness's subagent tool or a session manager (herdr, tmux) starting a CLI.
  • watch.py and dreamhub.py are stdlib-only, single-file, no build step, offline-clean, loopback by default.
  • Several targets on one host today; ssh-reachable hosts are wanted, and have no auth story yet (#275, #276).
  • Cost is per-session and dominated by the cache-warm tick: 4.75 min sits under the prompt-cache TTL, which is why the loop is cheap.
  • Single-writer durable state within a target. The multi-writer contract is #263's, and it is awaiting approval.

I1 and I2 fail G1 and G3 on measured history, not on prediction. Four orphaned watch.py servers were found in the guard ranges on 2026-07-25, one up 4.5 hours; two dreamers announced retirement in prose and stayed alive; three consecutive agents believed they had cleaned up. There is nowhere in the current design that would have said otherwise — and a richer read-only hub cannot fix it, because it can only show what a live coordinator chose to write.

The finding that most changes the shape of the answer: status.json's agents[] is session-ephemeral by design, and SKILL.md defends that correctly — it describes a running process, so committing it “would be a lie the moment it landed”. That defence holds for one session and breaks for N, because a dreamer outlives the coordinator that spawned it. The record of who is out has to outlive the coordinator too. See matrix 2.

I3 fails G4 because a daemon that assigns work is a second thing deciding what a target does next over one queue whose whole value is stable ids and ordering — the “never a third inconsistent queue” refutation with a different subject — and it duplicates SKILL.md's selection algorithm in code, where it will drift from the prose. I4 fails G1 because an agent watching agents shares their failure mode: it can go quiet and nothing notices. That refutes the metadreamer as the mechanism, not the metadreamer; matrix 6 keeps it.

The repair, and what the method bought

I6's single open cell was cost: three tiers do not by themselves make N dreamers cheaper than N timers. Matrix 5 finds that retire-when-idle satisfies G5 with no measurement and no new machinery — cost is sub-linear in idle dreamers if idle dreamers do not exist. So the recommendation is adoptable now, and the scheduler experiment becomes an optimisation with a known-safe fallback rather than a dependency the plan is betting on.

The shape being proposed

One sentence separates the tiers: the supervisor moves processes, the dreamer moves work, the hub is where the human stands.

J4 invents nothing, which is its main argument. ~/.config/dreamwork/worktrees/<slug>/claims.json already has every property a roster needs and they were already reviewed: coordinator-only writes, a monotonic revision for CAS, the state machine offered → claimed → working ⇄ blocked → ready → released plus stale, paths that must be disjoint while active, last_seen heartbeats, and a deterministic {basename}-{sha256(abs)[:12]} target slug rather than a basename that collides. Core owns the base record; the plugin keeps worktree and branch as its own fields on it.

J3's G9 entered as a ? and was resolved to ✘ by looking, so the cell says ✘ — two files describing which agents hold which paths is exactly how a claim and a roster come to disagree, and the disagreement gets discovered by an agent trusting the wrong one. J5 fails G7 today because #263 is unapproved, so nothing can land behind it; it is worth re-asking once the journal exists, and it is recorded here so that is a re-evaluation rather than a rediscovery.

the rule this settles
A lifecycle fact that outlives a session is written to the roster.
and its corollary
A fact describing this session is projected into status.json. If you cannot say which a new field is, it is the first one.

3 · Wake and steer — what carries an instruction?

IdeaAll G1G2G6 G8G10
K1 harness message only ✘ ✘✘✔✔✘
K2 file inbox + harness message — today's relay.py, then wake ✘ ✔?✔✔✘
K3 runtime adapter send-keys only ✘ ✘✘✔?✔
K4 durable intent + adapter wake + observed confirmation ✔ ✔✔✔✔✔
K5 c2c DM ✘ ✘✘✔✘?

K2 is what the loop does today and relay.py exists precisely to make it safe, so its ? is the interesting mark. Its gap is narrow and its own docstring names it: the inbox is durable but not delivered — an idle agent never reads it — so delivery is procedural, and nothing records whether the wake landed. A batch written two minutes after a dreamer went quiet sat unread indefinitely. K3 is the mirror fault: keystrokes into a TUI are delivery with no receipt. Having both faults in one system is the reason to stop treating durability and delivery as separate practices.

K4 adds the one thing neither has: the intent is a record with a state, and its confirmation is an observation — the process moved, the roster changed, the commit landed — not an agent's claim. It reuses #263's ternary Applied | NotApplied | Unknown rather than inventing a second proof vocabulary, and Unknown is a real outcome: a wake that may or may not have arrived is quarantined and shown, never assumed either way.

4 · Cross-host — how does an answer reach a loop on another machine?

This matrix answers a question that has been open in .dreamwork/questions.md since 2026-07-25.

IdeaAll G1G3G4 G7G8G11
L1 don't — same-host only ✘ ✔✔✔✔✔✘
L2 ssh in and append the remote questions.md ✘ ✘✔✘✔✘✔
L3 shared filesystem for .dreamwork/ ✘ ✘✔✘✔?✔
L4 remote intent to that target's own writer, over an ssh forward ✔ ✔✔✔✔✔✔
L5 hub-to-hub federation over authenticated HTTP ✘ ✔✔✔✘?✔
rec · L4
The target's own coordinator stays the only writer of its files. A remote human, hub, or metadreamer sends an intent to that target's receive endpoint; the local writer applies it and issues the receipt. An ssh forward is not a new bind, so loopback-only survives — and this is the shape daemon-mode.md already recorded for stage 3.
what it beat · L2
Appending the remote questions.md over ssh is two writers to one authority. The loop's own words when it filed the question: a wrong write corrupts another loop's record. L3 is the same fault with more machinery, and sync tools resolve conflicts by last-write-wins — the one resolution a durable record must never accept.

L5 is not wrong, only premature: it is blocked on auth (#275, #276) and it does not conflict with L4 — L4 is the transport L5 would eventually authenticate.

5 · Cost — what wakes N dreamers?

IdeaAll G1G5G7G12
M1 N per-session heartbeats (today, scaled up) ✘ ✔✘✔✔
M2 one host scheduler — event-driven wake, quiet backoff (#205) ? ✔?✔?
M3 retire-when-idle — no dreamer, therefore no timer ✔ ✔✔✔✔
M4 M2 and M3 together ? ✔?✔?

M1 fails by arithmetic. The tick interval is chosen to sit under the prompt-cache TTL, so an idle target's timer is a standing bill for keeping warm a cache nothing is reading. #205 already measured the single-target case: ~40 ticks in a day, most arriving mid-increment or mid-stream where the right action was nothing.

M2's two ?s point in opposite directions, which is why it needs a measurement rather than an argument: event-driven waking might cut total ticks substantially, or merely move them — and the risk to G12 is that a scheduler deciding a target is quiet while it is mid-increment makes active dreaming slower. The experiment is small: run one host for a fixed window with the scheduler behind a flag, count ticks against the same window on timers, and assert that a target with in-flight work never waited longer than 4.75 min.

M3 is a policy, not machinery, and the loop already believes it — DREAMWORK.md says retire idle dreamers rather than leaving them parked, SKILL.md says dreamers are batches, not careers. What is missing is that nothing enforces it and no record shows it happened, which is matrix 2's roster and matrix 3's observed retirement — both of which this plan builds first anyway. Its cost is the human's first steer to a retired target paying a cold start: his latency once, not a standing bill.

6 · The metadreamer

IdeaAll G2G4G5 G8G13G14
N1 none — the human is the only fleet manager ✘ ✔✔✔✔✔✘
N2 its own lifecycle path — direct spawn and kill ✘ ✔✘✘✘✘✔
N3 a client of the same lifecycle API the human uses: depth ≤ 1, budget lease, written delegation ✔ ✔✔✔✔✔✔

N3 costs nothing architecturally, which is the interesting part: same intents, same roster, same observed confirmations. Its bounds are three lines of policy — spawn depth ≤ 1 (a metadreamer may spawn dreamers; those may not spawn dreamers), a budget lease it cannot renew for itself, and a DREAMWORK.md delegation line in the shape plugin authority lines already use.

The constraint this yields, and it binds every stage below. Build no lifecycle path that only the human can use, and none that only an agent can use. The metadreamer must reuse the human's path, and the human must be able to do by hand anything the system does for him. A private path for either is how N2's failure arrives later wearing N3's name — which is why this is worth accepting now, while stage F is still far off and it is free to hold.

The ask

M1 · Adopt I6′ as the direction, authorizing stage A only?

rec
Three tiers, roster as the durable record, intents with observed confirmation, retire-when-idle. Authorizes stage A: a roster, a bounded CLI, orphan reconciliation, a read-only hub view. Stages B–F each return with their own plan.
alternative
Keep I1 and accept that a dreamer's existence is only ever as legible as its coordinator's memory. Defensible while there is one dreamer per human; the four orphans and the two prose-retirements are what it costs at N.

M2 · Fold L4's rule as the answer to the cross-host question?

rec
Never write another target's files; send an intent to its writer. Answers the question open since 2026-07-25 and lands in SKILL.md's durable-state section, where the trigger lives.
alternative
Leave it open. The cost is that the next agent facing a remote answer improvises, and L2 is the obvious improvisation.

M3 · Retire-when-idle before the scheduler?

rec
M3 first: no measurement needed, and stage B builds its prerequisites anyway. M2 becomes a measured optimisation with a known-safe fallback.
alternative
M2 first, on the argument that event-driven waking is the better end state. It is — but it is the one unmeasured claim in the plan, and betting the cost goal on it puts a ? on the whole direction.

M4 · Accept “no private lifecycle path” as a standing constraint now?

rec
Yes. Free to hold from the start, expensive to retrofit, and it is what keeps the stage-F metadreamer from needing a second mechanism.
alternative
Decide it when stage F arrives — at which point every stage-A-to-D path already exists in whatever shape was convenient.
