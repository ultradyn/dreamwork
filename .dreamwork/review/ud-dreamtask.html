ud-dreamtask

design review · task #50 · plan at .dreamwork/docs/plans/ud-dreamtask.md

A sister skill to dreamwork: the same philosophy — small verified increments, reflection over momentum, capture everything — pointed at finishing one task and then stopping. Dreamwork is a garden; dreamtask is an errand.

Where the two differ

Everything the two share — the tick flow, the reflection checklist, the guardrails, the commit discipline — dreamtask takes by reference rather than by copy. That is the whole design risk and the whole design opportunity: a second skill that duplicates the first will drift from it within a fortnight.

The part that earns its keep

Errands accumulate wavelength. Each dreamtask leaves a small ephemeral state directory behind, and when full dreamwork later initializes on that same target it harvests them: the wizard proposes Goals and Philosophy drafts from what the errands revealed, captured-but-unworked ideas become task seeds, and the ephemeral state graduates into the repo's durable .dreamwork/. You get a loop that starts already knowing you, instead of starting with an interview.

Four decisions

1. Can a dreamtask run inside an active dreamwork session?

Rec — standalone first
A sub-loop inside a running loop means two tick flows, two selection rules and one task list — the failure modes are the hard kind. Ship the errand alone, then compose once its shape is proven.
Alternative — sub-loop from day one
Tempting because "focus on this one thing" is exactly what a running dreamwork session sometimes needs. But that need is already served by do now.

2. Same 4.75-minute heartbeat regardless of task size?

Rec — yes, same cadence
The interval is set by cache economics, not by the work: it sits under the prompt-cache TTL. A short errand simply sees fewer ticks.
Alternative — scale with size
Sounds proportionate, reads as arbitrary: a slower heartbeat on a small task costs more, not less, because the cache goes cold.

3. State at ~/.config/dreamwork/tasks/<slug>/?

Rec — yes
Matches the machine-local precedent already set by roll state and the GitHub plugin's cursors, and keeps errand scratch out of a repo that never asked for it. Archived to tasks/archive/ on completion.
Alternative — in-repo
Visible and greppable, but an errand on someone else's repo would litter it, and the harvest story wants a single place to look.

4. Adopt dreamwork's guardrails wholesale?

Rec — yes, by reference
Commit markers, verification-before-completion, scope gate, the no-push default: inherited by pointing at ud-dreamwork, minus the rotation-specific parts. One source, no drift.
Alternative — restate them
A self-contained skill reads better standalone, at the cost of two copies of every guardrail — and this project has already watched duplicated rules drift apart within a day.
What lands, if you say go
  • A lean SKILL.md that references reflection.md and the shared conventions instead of copying them.
  • Init-lite: the acceptance-criteria wizard, dreamstate creation, the heartbeat.
  • The completion path: verify → wrap → offer learnings upstream → archive.
  • The harvest hook in ud-dreamwork's initialization, plus a migration entry.
  • A dogfood run on a real errand before it is called done.

The risk to name: this is a second skill with the same philosophy, and the failure mode is not that it works badly but that it slowly stops agreeing with its sibling. Everything shared must be referenced, never restated — and the coherence rotation should read both.
