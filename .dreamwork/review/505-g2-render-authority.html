The derived surface, concretely — and what it costs

What a wrapper is. A React component whose render calls the real builder and mounts its string — no JSX restatement of any markup, no second opinion about what a question card looks like:

export const QaCard = ({ q, k, ctx }) =>
  ambient(ctx, () => html(qaCard(q, k)));   // qaCard: client/components.js:586 — the one truth

The one authority stays the authority because the bundle is compiled from the same files watch.py serves — the build's entry concatenates client/*.js in the load order watch.py:530 already defines, then exports the wrapper shells. The load-bearing condition, stated as a rule for the bundle step: the build consumes client/, it never copies it. A copied builder is the second truth reintroduced with extra steps.

The ambient contract is small and enumerable. The builders read a handful of page globals; the wrapper's ambient() shim supplies them: data (components.js:158,192 — linkable_paths, entry lookups), view (components.js:686,705 — suppresses focus/roll chrome on the focus page), rmr (components.js:505 — reduced motion), and the submitCard handler a card's send button names inline (components.js:560) — stubbed in the design tool, where a preview's click has nothing to submit to. client/style.css (1,844 lines, real today) ships as the package's stylesheet unchanged.

The vocabulary already exists. components.js is not a monolith to be broken up before any of this works: qaCard ("THE question component", components.js:586 — its contract comment says every surface renders through it), expand, label, pipBtn, followThread, qaCompose, and the view builders (buildDashboard, views.js:878) are each one export-and-wrap away. Granularity in the tool equals the granularity we choose to export, and that list is a real starting set.

Honest costs — this is not free, it is bounded: hand-authored .d.ts for JS builders (the spec accepts it; contracts are only as good as we write them); curated fixture props for each .prompt.md so the design agent has realistic examples; the ambient shim is glue that must be kept honest (it is small, but it is ours); preview interactivity is dead by design (a stubbed submitCard — composition is the tool's job, submission is the dashboard's). None of these is a rendering decision, which is why none of them can diverge from the page.

Born-native surfaces are the other half of the same shape. Your session view never gets a string builder — it is written as a component from its first line, in the same system the wrappers live in, and the component tree is its one authority. The rule it must honour is the mirror of the wrapper's: a native component that needs a primitive the builders own consumes the wrapper, never re-derives it — one agePair, one label, one expand idiom, whoever is asking. This also quietly builds the road I3 lacked: if a builder-owned surface ever should go native, its wrapper is replaced by a native component as one surface-sized, reversible step — no flag day, no fork — and G2 holds at every point in between. The delta model rides the same split: a WS patch updates client state; builder surfaces re-render through the landed morph seam exactly as the 2s tick does today, and native surfaces apply the delta as component state.

The rule survives — and the tool agrees with it

The interesting thing this task was sent to chase: the apparent conflict is a point of agreement. Your rule — "two renderers only agree on the day they are written" — exists because parallel truths drift. Claude design's spec holds the same belief about its own ingestion: "ship what the customer already built … never a reimplementation", "not to hand-write a lookalike." The only options the two rules jointly refuse are the same options: the parallel library (I2) and the extracted approximation. The option they jointly permit is the derived bundle — which is, precisely, shipping what you already built.

And the sharpest apparent conflict dissolves the same way. A session view available "only via" a component system, while the dashboard keeps its string builders — is that not two maintained truths? No, and the rule's own birthplace says why: it was coined refusing "a JS row renderer beside the Python one" rendering the same rows (dreamhub-design.md:193–197), and #505's G2 wording carries the same scope — "exactly one place that commits the DOM for a view" (render-architecture.md). Two renderers of one surface drift; two surfaces each with one renderer have nothing to drift from. The drift risk in a heterogeneous page lives at the primitive level — a second agePair, a lookalike label — and that is exactly what the delegation rule above closes. This reading is Q1; it is asked, not assumed.

What would reopen this: if you want the design tool to recompose component interiors — drag the pieces inside a question card around as first-class parts — only a real migration (I3) delivers that, at the price its row shows: the incremental path forks qaCard, the honest path is a flag day, and every gesture in transitions.md is re-proven from scratch. Say so and #591 reopens with that goal on the board. Nothing in your stated focus asks for it, so it is priced here rather than asked.
