## The thing worth carrying: the trigger he names is evidence, not a cause

He reported #179 as *"when the git log at the top cycled just now, it
defocused the text box"*, and #151 — the commits panel — had landed that
morning. Every signal pointed at the new code.

The commits panel is innocent. The bug fires on **every** re-render of the
dashboard; I reproduced it on a plain `status.json` tick with no commit at
all. The panel is simply the one thing on that page whose re-render he can
SEE, so it is what he had in his eye when the box went dead.

The generalisation, and it is cheap: **before believing a reported cause,
fire the same bug on a different trigger.** One extra probe. Had I started
from #151's diff I would have spent the batch inside `regroupCards`, which is
correct code, and the real fault — a restore ordering in `tick()` — is not
reachable from there at all.

## Why the rule that already existed did not stop it

watch-design.md has said since #141 that human-owned state must survive the
tick, and `typing.mjs` guards it. Both were true and both were useless here,
for the same reason: **`typing.mjs` only ever visits `/questions`.** On that
route the cards are top level. On the **dashboard** they live inside `.qsec`,
the fold #141 itself added — and `focus()` on an element inside a closed
`<details>` does nothing and reports nothing. `restoreCardState` ran before
`restoreFolds`, so the box came back with his text and his caret in it, and
dead.

So the fourth instance of the rule was created by the third instance's own
feature, and the guard could not see it because a guard covers a route, not a
rule. The doc now says *any re-render* and puts an obligation on new render
paths; `motion.mjs` covers the dashboard.

The second layer matters more than the ordering: `refocus()` checks that the
focus actually landed and re-opens ancestors if it did not. Ordering fixes
this instance. The check kills the class — the next container someone wraps
this list in gets it for free, and it never has to know why.

## #184 does not reproduce, and that is the finding

Measured, on both routes, driving the real UI:

- **"answering #2 moves the question above it"** — the card above shows
  `steps=1 span=0 transforms=0` across 354 frames. It does not move.
- **"the git list updating moves the top question and rescrolls"** — across a
  full commit cycle, every question card: zero travel, zero transform; the
  panel height is constant at 112px on every frame. #151's fixed-height rows
  already make this true by construction, which was the cheap thing to check
  first and it paid.

Both are now regression checks in `motion.mjs` rather than a claim in a
report. The most likely explanation for what he saw is **#174** — the
departing row travelling *up*, against four rows travelling *down*, in a
panel directly above the question list. A gesture that fights itself reads as
"things moving that should not".

## Handing off: the submit morph moves its neighbours instantly

Found while measuring #184, out of scope, not fixed. `sendAnswer` restates
the card with `card.innerHTML = qaInner(...)` and **no snapshot and no
regroup**, so the card's height changes under its neighbours in one frame.
Measured: the cards below an answered card go `744 -> 791` in **2 distinct
positions** across 354 frames, with no transform — a teleport, in the one
gesture the page has most carefully taught to travel.

`regroup.mjs` is green over this because it answers by POST and lets the tick
do the whole move; only the morph path skips the regroup. The seam it needs
already exists (`snapshotCards` → `regroupCards`) and is exactly what the
`.qa details > summary` handler does three functions away.

Reported to the coordinator for the queue.
